# Loom consumer readiness

Assessment date: 2026-10-10.

This document collects the readiness findings from comparing Loom with the NIXL libfabric backend, AWS OFI NCCL, PyTorch Monarch, NCCL's network plugin interface, NVSHMEM, and Open MPI. The aim is to identify what Loom needs to support real consumers, using their existing transport operations as concrete requirements. It incorporates the agreed priorities and omits item 8 from the original discussion.

The next milestones should establish complete, predictable paths from provider discovery through registration, submission, completion, and teardown in working consumer integrations. Maintain these integrations under Loom's `examples/` directory, using Nix to build pinned consumers with Loom backend patches. Several consumers can advance together, each with explicit supported configurations and acceptance criteria. Loom already provides much of the API surface; the work is making those pieces compose without losing information or weakening lifetime guarantees.

Correctness is the governing constraint. Promoting information and decisions to compile time wherever possible is a central design goal, and duplicating upstream libfabric constants is an intentional part of that design. A runtime check may be removed only when its condition is guaranteed by the static contract or established by validation that remains valid for the operation's lifetime. Otherwise, retain the runtime check. Compile-time specialization must preserve the same correctness guarantees as a fully checked path.

These findings describe the source examined during the scan. The small reproductions used implementation headers and mock resources; they were not hardware validation or performance measurements.

The [upstream source audit](#upstream-source-audit) below cross-references the local libfabric checkout and adds confirmed conversion, provider-trait, and DMA-BUF findings. Those findings take priority alongside the original correctness defects.

## What the consumers tell us

NIXL separates backend protocols, rail management, and low-level libfabric operations. Loom can simplify the last layer substantially: resource ownership, registration, submission, completion handling, and error propagation. NIXL still needs its transfer aggregation, metadata exchange, notifications, and rail policy. Its operations require explicit destinations, registered buffers, immediate data, operation flags, and sometimes completion source addresses.

AWS OFI NCCL already has resource wrappers and structured ownership, so its potential benefit is less about replacing raw handles with RAII. The stronger test is whether Loom can express its registered tagged messages and RMA operations while preserving backpressure, completion information, and progress control. Its eager messages, remote-registration protocols, and partial progress across rails expose gaps that simple examples do not.

Monarch adds a Rust consumer with an actor runtime, allocation keepalives, GPU buffer views, and batched reads and writes. Its existing backend boundary is a plausible place to use Loom, but the Rust frontend currently cannot express the registered RMA path. It also exposes gaps in threading, operation retention after a timeout, and progress when a process only exports memory. The [Monarch assessment](#monarch-consumer-requirements) below distinguishes these Loom requirements from changes that belong in Monarch.

NCCL's own plugin contract adds requirements that inspecting AWS OFI NCCL alone does not fully establish: ordered receive groups, retryable group admission, actual per-buffer receive sizes, GPU visibility after receive completion, registration reuse across connections, and separate network-completion and GPU-consumption lifetimes. Its [plugin assessment](#nccl-network-plugin-requirements) below also identifies a connection-event ownership defect and missing discovery information. A basic host-driven network plugin does not require collective offload or GPU-initiated networking.

NVSHMEM adds remote-completion watermarks, selective CQ completion, registered atomics, and batched RMA with `FI_MORE`. Open MPI adds MPI probes and claimed messages, scalable receive-context addressing, and allocator-monitor integration. Its separate usNIC transport also exposes prefix-buffer and asynchronous address-insertion requirements. The [combined assessment](#nvshmem-and-open-mpi-consumer-requirements) below distinguishes missing operations from existing wrappers that lose required information. Open MPI's generated specializations provide a concrete precedent for Loom's compile-time approach.

Topology decisions, multirail scheduling, NCCL matching, and NIXL notification protocols should remain consumer responsibilities. Loom should supply reliable, inexpensive transport operations that can express those protocols.

## Fix confirmed correctness defects first

Small compiled reproductions exposed these issues:

| Finding                                                                                        | Consequence                                                            | Required behavior                                                                                                |
| ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `fabric_info::iterator` remains on the current entry when a next entry exists.                 | Enumeration can repeat the first provider or device indefinitely.      | Advance to each entry and eventually reach the end.                                                              |
| `request_context_pool` grows a vector containing outstanding contexts.                         | Growth can invalidate addresses already handed to libfabric.           | Context addresses remain stable until the associated operations are finished.                                    |
| Moving `typed_request_context` preserves the base class pointer into the source object's data. | The moved-to object can refer to the source's storage.                 | Move semantics preserve the relationship between a context and its own payload, or movement is prohibited.       |
| `mr_cache::invalidate` skips active entries without excluding them from subsequent lookup.     | New users can acquire a registration that was meant to be invalidated. | Invalidation immediately prevents new acquisition, while existing holders retain the registration until release. |

Relevant code: [fabric iteration](include/loom/detail/impl/fabric_impl.hpp), [request contexts and pool](include/loom/core/request_context.hpp), and [MR cache](include/loom/core/mr_cache.hpp). The iterator implementation also appears in [src/fabric.cpp](src/fabric.cpp).

The reproduction reported:

```text

pool_growth_frees_outstanding_context_storage=1
moved_context_points_to_own_data=0
lookup_reuses_live_invalidated_registration=1

```

The final result is a cache behavior gap, discussed below. The first four were correctness defects at the original reproduction revision. During the later NCCL source pass, the iterator advances through `next_entry`, and cache invalidation marks active entries ineligible for lookup and retires them after release. ## 1. Complete the operation interface across frontends

The core RMA interface can carry an explicit peer and a local memory registration, but the frontends do not consistently preserve that information. The sender RMA operations use `endpoint::read` and `endpoint::write`, whose implementation supplies a null local descriptor and `FI_ADDR_UNSPEC`. The Asio RMA operations accept a registration but lack an explicit peer argument.

This prevents some registered RDM operations from being expressed through every frontend even though the core has the necessary pieces. See [endpoint implementation](include/loom/detail/impl/endpoint_impl.hpp), [sender operation states](include/loom/execution/operation_state.hpp), and [Asio endpoint](include/loom/asio/basic_endpoint.hpp).

A common operation representation should retain:

- Local buffers and the corresponding registration descriptor for each IOV entry.
- The destination peer.
- Remote address, length, and key for RMA.
- Immediate data where supported.
- Operation flags and the requested completion behavior.
- The operation context.

Core calls, callbacks, Asio, senders, and the Rust bridge should share the submission primitive. Convenience overloads can populate the representation without limiting what the complete interface can express. A common representation need not erase compile-time information: statically known flags, capabilities, and buffer shapes should remain available for constraints and specialization.

The Rust [FFI declarations](bindings/rust/src/ffi.rs) define remote-memory metadata but expose no RMA read or write operation. Monarch needs the existing C++ registered, explicit-peer operations to be usable from Rust, including local descriptors, remote address and 64-bit key, completion policy, and valid operation-context storage. Providing an FFI type without the corresponding submission path does not complete that frontend.

NVSHMEM and Open MPI expose the same problem in the core atomic interface: its submissions use `FI_ADDR_UNSPEC`, and compare-and-swap cannot carry a descriptor for the replacement operand. Complete explicit-peer atomic submissions with separate operand, comparison, and result registrations, plus operation flags. Open MPI also requires tagged peek/claim operations; a tagged receive wrapper without those semantics is not a complete matching interface.

**Acceptance criterion:** the same registered, explicit-peer RDM write with immediate data and operation flags can be expressed through each frontend with equivalent semantics.

## 2. Complete compile-time contracts and validate their assumptions

Loom should express as much of a consumer's transport contract as possible at compile time. Its [provider traits](include/loom/core/concepts/provider_traits.hpp) and [capability queries](include/loom/fabric_query.hpp) already provide a basis for that approach. Traits can encode guarantees, requirements, and implementation choices that support static dispatch and compile-time rejection of invalid combinations.

The distinction to preserve is what a constant promises:

- Upstream API constants, such as flag values and enum encodings, can be mirrored as compile-time values. Where applicable, compile-time assertions against the supported libfabric headers should detect drift. Many existing Loom flags instead use a distinct public bit layout with constexpr conversions; for those, verify the conversions rather than requiring numeric identity. The source audit passed 78 assertions for supported individual flag mappings, while finding separate defects in ordering conversion and omitted information.
- Provider invariants can be compile-time traits within their documented provider, version, and configuration scope. Record the upstream basis for those guarantees and establish that the selected environment falls within that scope. Unverified assumptions must not authorize operations or remove required checks.
- Consumer requirements and chosen bounds can be compile-time parameters even when the environment must be checked at setup. A required CQ data width or a chosen inject bound is useful static information.
- Values that depend on the selected device, endpoint, or configuration need discovery or validation. An upstream default or maximum does not by itself establish the corresponding guarantee for every instance.

For example, a consumer can require four bytes of CQ data as part of its type-level contract, request that capability during discovery, and validate the returned configuration before constructing the usable endpoint. Likewise, an inject path specialized for a fixed bound can validate that the selected endpoint supports at least that bound during setup. Each submitted payload must still fit that bound, established statically where possible and checked at runtime otherwise. Changes to configuration that invalidate a checked assumption must also invalidate or revalidate the associated contract before further submission.

Required runtime validation must remain effective in release builds. If a static requirement is not met, return an error before exposing the specialized path, or select a checked fallback only when it preserves the operation's promised semantics. Static dispatch must also preserve handling of runtime submission failures, backpressure, and asynchronous errors. Tests should cover rejected configurations and boundary violations as well as successful specialization.

Expose the information needed to establish those contracts: ordering, MR modes, threading requirements, CQ data width, key size, message and RMA size limits, inject limits, IOV limits, and transmit/receive attributes. AWS OFI NCCL's four-byte CQ data requirement is a concrete example that the current `fabric_hints` cannot express. The requested libfabric API version could likewise be a compile-time contract parameter; discovery currently selects it from the build headers. See [fabric hints](include/loom/core/fabric.hpp) and [discovery implementation](include/loom/detail/impl/fabric_impl.hpp).

NCCL also makes tag-format negotiation and device identity concrete requirements. A tagged protocol must validate the available tag fields before reserving bits for connection and sequence identifiers; `uint64_t` storage alone does not promise 64 usable bits. Expose provider-reported NIC, PCI, and link information where available so the consumer can build truthful device properties. Topology and wire-tag layout remain consumer policies.

Default TX/RX operation flags and their overrides are part of the contract too. NVSHMEM requests `FI_DELIVERY_COMPLETE` to implement `quiet`; Open MPI's OFI BTL also requests delivery completion, while its MTL requests send-after-send ordering on both transmit and receive attributes. Returning generic capability bits without preserving those requested semantics is insufficient. These defaults and ordering requirements are suitable static profile parameters, established by checked construction.

At the original scan, the RMA limit helpers returned fixed values of 1 GiB and 4096 bytes. A subsequent source check found that the [RMA implementation](include/loom/detail/impl/rma_impl.hpp) now queries endpoint options and falls back to stored provider attributes. The earlier fixed-return finding is therefore historical. Compile-time bounds remain appropriate when their guarantee is established by the supported configuration or validated during setup.

**Acceptance criterion:** consumers can express statically known requirements, reject statically invalid combinations, and retain compile-time dispatch after any necessary setup validation. Mirrored constants have a clear upstream basis, and traits distinguish guarantees and chosen requirements from defaults or environment-dependent limits. A mismatch cannot expose an invalid specialized path, and every omitted runtime check has an established guarantee covering the actual operation.

## 3. Make registration configurable and cache policy explicit

A registration request needs to combine the parameters real consumers use: permissions, requested key, memory interface and device, DMA-BUF mapping information including its buffer offset, and endpoint binding or enablement when required by the provider. The general `fi_mr_attr.offset` field is reserved and must remain zero; it is distinct from `fi_mr_dmabuf.offset`.

These are not independent alternatives. A consumer may need DMA-BUF registration with a particular heterogeneous-memory interface and device. The current `register_dmabuf` interface does not carry all of those parameters and uses a requested key of zero. It also copies the buffer offset into the reserved registration offset, which the upstream audit confirmed with a mock submission. See [memory registration implementation](include/loom/detail/impl/memory_impl.hpp) and libfabric's [registration contract](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_mr.3.md).

Caching should be a policy layered on a complete registration interface. A safe cache identity needs to account for the domain, relevant endpoint, permissions, memory interface and device, allocation identity, and covered range. Reuse of a virtual address after an allocation is freed must not silently reuse the old allocation's registration.

The current `lookup_hmem` and DMA-BUF lookup paths create registrations on repeated calls rather than finding reusable entries. Either implement the advertised reuse or make the registration-only behavior explicit. See [MR cache](include/loom/core/mr_cache.hpp).

Retention also needs an intentional contract. AWS OFI NCCL's cache removes an entry when its last reference is released; Loom retains unused entries until eviction. Either policy can be useful, but a consumer needs to understand resource retention and how it interacts with allocation lifetimes.

NCCL's optional `regIsGlobal` promise is stronger than having a cache: preregistering a range through one connection must support inexpensive registration of contained subranges through other connections, with correct final deregistration. Domain and endpoint scope, HMEM/DMA-BUF identity, and pin/release policy must support that promise before a plugin advertises it. A connection-local implementation can leave the property disabled.

Invalidation must separate two events: immediately excluding an entry from new lookups, and deregistering it once outstanding holders release it. Skipping an active entry does not implement that separation.

**Acceptance criterion:** registration supports the necessary parameter combinations, and register/use/invalidate/reallocate sequences cannot return stale registrations or prematurely deregister active ones.

## 4. Preserve full completion semantics

The completion abstraction already carries context, status, size, flags, tag, and immediate data. Real consumers also need source addresses and, for applicable completion formats, the received buffer pointer. Each field needs a clear validity rule. See [completion queue interface](include/loom/async/completion_queue.hpp).

In particular, the native CQ `len` is not a universal count of bytes transferred by any operation. The [CQ contract](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_cq.3.md) defines it for receives and applicable remote-write events. An NCCL adapter must retain the submitted send length and report actual receive lengths in the original group order, rather than use the CQ size field indiscriminately.

CQ format must also be selectable and decoded correctly. Loom currently always creates a tagged CQ; Open MPI uses context-only queues for some paths, and upstream usNIC rejects tagged format. NVSHMEM needs `fi_cq_readfrom` source addresses. Open MPI probing additionally requires preserving `FI_ENOMSG` as an operation-specific no-match result rather than turning every CQ error into a fatal transport failure.

A local completion usually identifies an operation through its context. A remote event may instead be identified through flags, immediate data, and its source, without a local operation context. Both must work on the same queue where the provider and application configuration permit it.

The sender `poll_completions` path currently assumes its own operation-context representation and rejects null contexts. That is insufficient for a queue carrying unsolicited remote events or operations from multiple dispatch mechanisms. Generic CQ reading should preserve the event, with frontend-specific dispatch layered above it. See [sender completion dispatch](include/loom/execution/operation_state.hpp).

Error details need equivalent care. `cq_error_info` exposes an `err_data` pointer. Loom supplies no error-data buffer to `fi_cq_readerr`, so libfabric's documented borrowed-data rule applies: provider-owned data remains valid only until a subsequent CQ read. The lifetime must be explicit, or the data must be captured before further reads when it needs to survive for deferred reporting. See libfabric's [CQ error contract](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_cq.3.md).

**Acceptance criterion:** local completions, remote events, and errors can share a supported CQ configuration without losing attribution, discarding meaningful events, or interpreting a foreign context as a frontend's operation state.

## 5. Publish progress and backpressure contracts

The core submission interface should distinguish accepted work, temporary unavailability, and permanent failure while remaining nonblocking. Optional retry machinery should have bounded work per progress call, fairness rules, and queue limits.

AWS OFI NCCL provides an important partial-progress case: some rail submissions can succeed before a later rail returns `FI_EAGAIN`. Retrying must preserve that accepted work and resume from the correct point. Loom need not own the rail scheduler, but it must make submission outcomes precise enough for that scheduler to avoid duplicate operations.

Document who drives progress, which thread invokes callbacks, whether callbacks may submit more operations, and how the negotiated threading mode affects locking. Consumers such as NIXL and NCCL also need a budgeted manual progress interface they can integrate into an existing loop.

Progress may be required at an RMA target even when it has no outstanding local operations and expects no completion events. Libfabric's [manual-progress contract](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_domain.3.md) explicitly covers that case. Monarch's verbs CQ actor polls according to expected completions; copying that policy into a Loom backend can leave remotely accessible buffers without progress. Rust also needs structured submission errors: the current C++ bridge turns errors into exception messages, so its `WouldBlock` variant does not reliably identify submission `FI_EAGAIN`.

Asio's `use_fd_polling` option currently exists while progress is driven by a timer. Implement the option's behavior or remove the unsupported promise. See [Asio fabric service](include/loom/asio/fabric_service.hpp).

**Acceptance criterion:** injected temporary submission failures do not produce duplicate accepted work, unbounded retry loops, starvation, or ambiguity about who must call progress next.

## 6. Define completion, cancellation, and destruction precisely

Submission acceptance, local completion, remote notification, and GPU visibility are different milestones. APIs should name the milestone they provide and explain when buffers may be reused. They should also state when additional provider-specific visibility operations are required.

For example, the synchronous Asio `send` helper is documented as blocking but returns after submission. Its name and documentation should reflect that behavior, or the implementation should wait for the promised completion. See [Asio endpoint](include/loom/asio/basic_endpoint.hpp).

Specify the ownership and borrowing relationships among fabrics, domains, endpoints, CQs, registrations, buffers, and operation states. Shared ownership is not required everywhere; predictable lifetime requirements are.

Separate the lifetime of an accepted operation from the lifetime of the future observing it. Monarch retains memory and registration views while work is outstanding, even when a caller times out or drops its result. Loom needs an ownership or retention contract that permits this safely. Keeping an allocation alive prevents deallocation; it does not by itself make conflicting buffer access or reuse safe while DMA remains in flight.

Some native contexts must survive even successful completion. Libfabric requires the same context for a successful tagged peek-and-claim and the later receive of that claimed message. Model that reservation explicitly; recycling operation storage at the first completion loses the provider's claim identity.

Provide an explicit fallible close path so consumers can observe unsuccessful teardown. Destructors that ignore `fi_close` errors do not provide enough information to determine whether resources were successfully released.

Cancellation needs a contract for unsupported cancellation, races with completion, exactly-once delivery of the terminal result, and the point at which operation storage and buffers become reusable. Asio already retains endpoint state and has cancellation tests; the work is to make the guarantees complete and consistent across the API.

Libfabric cancellation is asynchronous. Endpoint close can discard outstanding operations without reporting completions and may discard previously completed CQ entries. Loom must therefore either require draining operations before close or explicitly resolve its own pending operations during teardown; it cannot derive exactly-once frontend reporting from provider completions after close. See the `fi_cancel` and `fi_close` sections of the [endpoint contract](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_endpoint.3.md).

**Acceptance criterion:** pending-operation cancellation and teardown have observable outcomes, stable operation storage, exactly-once terminal reporting, and unambiguous buffer lifetimes.

## 7. Make allocation-free steady-state operation achievable

Transport consumers need control over allocations in submission and progress paths. The messaging wrapper currently constructs a vector of raw registration descriptors for an operation, and the Asio service copies its CQ list into a vector during polling. See [messaging](include/loom/core/messaging.hpp) and [Asio fabric service](include/loom/asio/fabric_service.hpp).

Use stack or caller-provided scratch space where appropriate, reusable prepared descriptors, and stable context pools. If PMR is part of the allocation contract, supporting paths should not bypass it with unrelated standard allocations.

Validate the contract with an allocator that rejects allocations after warmup. Also inject allocation failures after native-resource creation to verify that an exception or allocation error does not leak the newly created resource.

**Acceptance criterion:** selected messaging, RMA, and completion paths can run after warmup without allocating, and allocation failures during setup release resources correctly. This is a proposed validation target, not a measured performance claim.

## Consumer-shaped validation experiments

These experiments exercise the boundaries between components rather than merely checking individual wrappers.

| Experiment                                                                                                             | What it should establish                                                                                                                                                |
| ---------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Three RDM peers exchanging registered tagged messages.                                                                 | Enumeration terminates; peers are selected correctly; registration descriptors and completion attribution survive the full path.                                        |
| A two-rail write with immediate data and injected `FI_EAGAIN`.                                                         | Each accepted segment is submitted once; retries resume correctly; remote events can be attributed and aggregated.                                                      |
| A host header and GPU payload in one message.                                                                          | Mixed-memory IOV registration, HMEM metadata, and the intended allocation behavior compose correctly.                                                                   |
| Register, use, invalidate, and reuse an allocation.                                                                    | Cache identity distinguishes allocations; invalidation excludes new users; active holders delay deregistration safely.                                                  |
| Cancel and close with operations pending.                                                                              | Context addresses remain valid; ownership and teardown rules hold; terminal results are delivered exactly once.                                                         |
| Submit a Rust batch of registered reads and writes to distinct remote buffers.                                         | Explicit peers, checked subranges, opaque local descriptors, remote keys, and completion attribution survive the FFI boundary.                                          |
| Export a buffer from an otherwise idle peer using a manual-progress provider.                                          | Remote reads and writes finish even when the target has no pending local request or awaited future.                                                                     |
| Inject `FI_EAGAIN` and an asynchronous error into a partially accepted Rust batch, then time out or drop its observer. | Accepted work is not duplicated; contexts, registrations, and allocations remain valid; other operations' completions are preserved; final retirement is accounted for. |
| Register GPU subviews from multiple devices, then release and reuse an allocation.                                     | Device identity, DMA-BUF offsets, remote address models, registration retention, and allocation identity remain correct.                                                |
| Attempt peer setup with incompatible provider profiles or register an unsupported memory class.                        | The consumer can reject the configuration before publishing unusable metadata or starting DMA.                                                                          |

Start with mock-provider fault injection to force rare conditions, including temporary submission failure, allocation failure, cancellation races, and provider use of all `fi_context2` storage slots. Then repeat the operation shapes on a software provider and the targeted hardware. Mock success does not establish hardware readiness or GPU visibility guarantees.

Existing tests are useful, but their assertions need to exercise the behavior at issue. For example, the provider-range test in [test_fabric_query.cpp](tests/test_fabric_query.cpp) checks `range.empty() || !range.empty()` without iterating, so it cannot detect the iterator defect.

## Working consumer integrations under `examples/`

Implement and maintain real consumer backends under Loom's `examples/` directory. These examples should run the consumers' actual workloads through Loom and serve as executable specifications for the contracts described here. Nix-managed source pins, dependency selections, and patches make it practical to maintain several integrations as Loom and upstream consumers evolve. Use the existing [flake](flake.nix) as the entry point for their builds and development environments.

Suggested integration directories and initial acceptance targets:

| Directory                | Working integration and what it should exercise                                                                                                                                                                                             |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `examples/nixl/`         | A Loom backend running NIXL transfers, registration reuse, notifications, and teardown; extend to heterogeneous memory and multiple rails.                                                                                                  |
| `examples/nccl/`         | A Loom network plugin loaded by NCCL and exercised by collective workloads, starting with a host-driven, single-receive profile and correct retry and request accounting.                                                                   |
| `examples/aws-ofi-nccl/` | A patched AWS OFI NCCL transport using Loom beneath its existing protocols, exercising registered messages and RMA, partial progress, and backpressure. This tests the existing implementation's demands separately from a new NCCL plugin. |
| `examples/openmpi/`      | A patched Open MPI OFI component running MPI workloads, including tagged matching and probe/claim for the MTL path. Add BTL atomics and scalable contexts as separately validated configurations.                                           |
| `examples/nvshmem/`      | A patched NVSHMEM libfabric transport running remote-memory operations, atomics, and quiet, with explicit checks of the remote-completion guarantees used by its host and GPU paths.                                                        |
| `examples/monarch/`      | A Loom Rust backend running Monarch's registered read/write workloads, including idle-target progress and operation retention after timeout or observer drop.                                                                               |

Each directory should contain the integration-specific source or upstream patch series, a Nix build definition connected to the root flake, runnable workload or test entry points, and a README with exact build and run commands. Pin the upstream consumer and relevant dependencies, and build against the Loom checkout being developed. Share common dependency definitions where useful. Keeping upstream source pinned and applying local patches avoids needing a full source copy in each example.

Record each integration's supported provider and endpoint configuration, memory types, progress and threading policy, required hardware, and currently exercised operations. Distinguish successful compilation, software-provider execution, and hardware validation. A hardware-dependent run should report an unmet prerequisite explicitly. Successful execution must establish that the intended Loom backend handled the workload; a silent fallback to another transport does not validate Loom.

Use the consumer's existing correctness tests where they cover the relevant behavior, and add targeted workloads or fault injection for the gaps identified in this document. Check transferred data, completion and lifetime semantics, error propagation, and resource retirement. Compare with the existing transport when useful, and record performance measurements separately from correctness results. Passing a build or a small transfer does not establish GPU visibility, cancellation safety, or every supported provider combination.

The integrations should also test Loom's compile-time design. Identify choices fixed during consumer setup, validate the selected environment, and carry those established guarantees into specialized operation paths. Preserve runtime checks for facts that setup cannot establish. Exercise rejection of incompatible configurations alongside successful workloads, so specialization cannot quietly authorize unsupported operations.

Develop these examples alongside Loom's fixes. Repeated setup code can reveal a missing shared abstraction; reconstructing information discarded by Loom reveals an incomplete interface; repeated ownership bookkeeping can reveal a lifetime contract worth expressing in the API. Keep consumer matching, scheduling, and application protocols in their integrations. Broad consumer coverage is useful evidence for the abstraction, and each integration can reach working milestones independently. The unit of completion is a tested consumer path with stated guarantees.

## Suggested implementation order

Use the following as priorities within each integration. Begin the `examples/` backends early and let their workloads expose missing contracts as the library develops; completing the entire API is not a prerequisite for starting a consumer port.

1. Resolve the confirmed defects against the current revision, retaining focused regressions for fixes already made. This includes context storage, conversion, registration, and provider-trait findings, plus connection-event ownership if connected endpoints are used.
2. Complete registered RDM messaging, RMA, and atomic operations across the needed frontends, including Rust. Add probe/claim semantics for matching consumers, and preserve the required CQ information and structured submission errors.
3. Complete compile-time capability contracts, the discovery and setup validation needed to establish them, and registration, progress, and lifetime contracts.
4. Run the consumer-shaped experiments through the working `examples/` integrations and use failures to refine those contracts. Keep focused mocks for conditions that real workloads cannot reliably force.
5. Refine asynchronous behavior and verify allocation-free steady-state paths.

The readiness work should strengthen Loom's chosen design. A useful completion criterion is that representative NIXL, AWS OFI NCCL, Monarch, NCCL, Open MPI, and NVSHMEM workloads run through Loom in the documented example configurations with their required information and guarantees intact, while their protocols and scheduling policies remain with the consumers. Keep those integrations runnable as regression checks as Loom evolves.

## Upstream source audit

### Scope and evidence

Cross-reference performed against `/home/sielicki/libfabric` at commit `a79c42e5de63eadae8e3dfc7e172af639a6161b9`, described by Git as `v2.7.0rc1-219-ga79c42e5d`. Its headers identify API version 2.7. Loom source was checked through commit `63a7bdd6cef326ac2d5f85a47cb65cfad292929d`. These are snapshot findings; provider behavior can differ by version, protocol, and negotiated configuration.

The audit read public headers, provider implementations, shared utility code, and the manual sources in that checkout. A C++26 probe compiled directly against the cloned headers passed 78 static assertions covering both directions of 18 capability, five mode, and nine MR-mode mappings, plus six MR-access, three CQ-bind, and five operation-flag mappings in the outbound direction. A separate mock registration captured the exact attributes Loom submits for DMA-BUF registration. No libfabric provider or hardware was exercised; the registration mock also stubbed error-string formatting.

This supports Loom's compile-time approach: its supported individual mappings can be checked against upstream at compile time. The defects below concern inaccurate guarantees, lossy conversion, and incorrect parameter semantics.

### Conversion findings

| Finding                                                             | Evidence and consequence                                                                                                                                                                                                                                                                                                                                                                                                    | Required change                                                                                                                                                                                                     |
| ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Partial message ordering becomes strict ordering.                   | In [fabric.h](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/include/rdma/fabric.h), `FI_ORDER_STRICT` is the composite mask `0x1ff`. Loom's [from_fi_order](include/loom/detail/conversions.hpp) tests whether any bit overlaps. `FI_ORDER_RAW` alone therefore sets Loom's strict flag, and converting back yields 511 instead of 2. ### Registration and resource lifetime findings

**DMA-BUF offsets are two different fields.** Upstream's [fi_mr_attr and fi_mr_dmabuf definitions](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/include/rdma/fi_domain.h) contain both offsets. The [MR contract](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_mr.3.md) reserves the registration offset as zero while permitting a DMA-BUF offset. [EFA's registration implementation](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/prov/efa/src/efa_mr.c) passes the DMA-BUF offset to its device registration and derives the virtual address from `base_addr + dmabuf.offset`. Loom currently copies the offset into both fields and defaults the interface to system memory. The mock captured:

```text
dmabuf_offset=4096
mr_attr_offset=4096; required=0
iface_defaults_to_system=1
```

Correct the reserved offset, expose the needed interface/device information, and make the exported remote address consistent with the registered range and its address model.

**Virtual addresses and MR-relative offsets need distinct contracts.** Every current provider trait computes `base + offset`, and [provider_remote_memory::from_mr](include/loom/core/provider_aware.hpp) always exports the allocation's virtual address. Upstream requires MR-relative target addresses when `FI_MR_VIRT_ADDR` is absent. The behavior is visible in [util_mr_map.c](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/prov/util/src/util_mr_map.c): registration stores the region base for offset-based addressing, and verification adds that base to the received target offset. Exporting an allocation address in such a configuration is incorrect. Address-model specialization is useful compile-time information, provided it matches the registered region's actual contract.

**Registration requirements include the memory interface.** The [MR contract](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_mr.3.md) allows `FI_MR_HMEM` without `FI_MR_LOCAL`: host buffers may avoid local registration while device buffers still require valid descriptors. EFA's ordinary RDM handling of `FI_MR_LOCAL` therefore does not establish that every buffer may omit its descriptor. `FI_MR_ENDPOINT` also explicitly requires binding and enabling the registration before use.

**Provider context storage belongs entirely to the provider.** [fabric.h](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/include/rdma/fabric.h) defines eight internal pointer slots in `fi_context2`; the [getinfo contract](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_getinfo.3.md) requires stable, opaque storage through operation completion or completed cancellation. This confirms the severity of the context-pool relocation defect. Loom's current [safe_context](include/loom/core/safe_context.hpp) correctly puts application metadata after the provider-owned storage; retain that separation.

**Completion and teardown require explicit ownership.** [fi_eq.h](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/include/rdma/fi_eq.h) includes received-buffer pointers, error source addresses, and the borrowed lifetime of error data. The [CQ contract](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_cq.3.md) also permits errors without operation contexts, including failures of operations that requested no success completion. The [endpoint contract](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_endpoint.3.md) makes cancellation asynchronous and permits close to discard work without completions. These source details reinforce the completion-preservation and frontend-lifetime requirements above.

### Consequences for implementation and verification

1. Correct the ordering conversion and provider-trait contradictions before relying on them for static dispatch. Correct the DMA-BUF offset independently of broader registration API work.
2. Add upstream-backed constexpr checks for supported mappings and round trips. Include composite masks and negative cases so partial ordering cannot become strict, and missing capabilities cannot silently appear supported.
3. Establish provider/profile requirements when constructing specialized resources. Test incompatible progress modes, zero inject limits, different MR address models, and missing atomic operation support as rejected configurations.
4. Preserve compile-time specialization for established guarantees. Retain runtime checks for dynamic payload sizes, configuration-dependent facts that have not been established, and operation failures.
5. Exercise real providers after the source and mock checks, using the consumer-shaped experiments above. Source inspection establishes contracts and defects; it does not establish end-to-end hardware behavior.

## Monarch consumer requirements

### Scope and consumer boundary

This assessment inspected `/home/sielicki/monarch` at commit `dd1bb6719b2cf2b6bdf8851df02f092a900e6f5e`, Loom through commit `8705a8249a0ab57850451c6b9ab5b13d35971b03`, and the libfabric checkout identified above. It is a source review, not a backend implementation, compilation result, or hardware test. Earlier findings remain snapshots of the code examined at their stated revisions.

Monarch's [RdmaBackend trait](https://github.com/meta-pytorch/monarch/blob/dd1bb6719b2cf2b6bdf8851df02f092a900e6f5e/monarch_rdma/src/backend.rs) is the useful integration boundary. A backend discovers availability, starts its resources, registers and releases remotely accessible buffers, and submits batches with a timeout. Its remote-buffer context must be serializable, and the backend itself must be `Clone + Send + Sync`. The registered implementations are Mellanox verbs, EFA verbs, and TCP. A Loom implementation would be another backend at this boundary; the lower-level `IbvQueuePair` abstraction depends on verbs resources and is not a transport-neutral interface.

The initial transport requirements are modest: registered reads and writes, endpoint-address exchange, remote registration metadata, and batch completion accounting. Monarch's [operation definitions](https://github.com/meta-pytorch/monarch/blob/dd1bb6719b2cf2b6bdf8851df02f092a900e6f5e/monarch_rdma/src/lib.rs) distinguish reads into local memory from writes out of local memory. Reads transfer the remote range into a sufficiently large local range; writes transfer the local range into a sufficiently large remote range. The adapter must preserve those different size rules. Tagged matching, atomics, and native GPU queue access are not prerequisites imposed by this backend trait.

The following gaps make Monarch useful as a readiness test for Loom.

### Registered RMA and discovery must be usable from Rust

Loom's [core RMA operations](include/loom/core/rma.hpp) already accept a local registration, explicit peer, and remote address/key. Its [Rust bridge](bindings/rust/src/ffi.rs) exposes messaging, basic registration, endpoint names, and address-vector insertion, but no RMA submission. Rust discovery hints contain only provider name, capabilities, and endpoint type; they do not provide the NIC/domain selection and negotiated attributes needed to establish a consumer's transport contract.

Complete this particular path before aiming for broad binding coverage. Rust needs registered read/write operations, checked lengths and offsets, opaque local registration descriptors, 64-bit remote keys, requested completion semantics, and discovery results sufficient to validate threading, progress, MR modes, and memory-interface support. It must also be possible to select the intended device/domain rather than silently accepting the first suitable result. Device pointers must be expressible without constructing a Rust slice that claims host-accessible memory.

This is compatible with compile-time promotion. A consumer can select a compiled provider/profile implementation and validate its requirements during setup; the bridge need not turn every internal decision into runtime dispatch. Facts crossing FFI still need accurate representations, and a profile must not promise guarantees that discovery has not established.

### Thread ownership needs an explicit Rust contract

The Rust [resource wrappers](bindings/rust/src/lib.rs) retain their parents through `Rc`, making those resource graphs neither `Send` nor `Sync`. This preserves useful ownership relationships, but they cannot be placed directly into Monarch's ordinary actors or futures: [actors require `Send`](https://github.com/meta-pytorch/monarch/blob/dd1bb6719b2cf2b6bdf8851df02f092a900e6f5e/hyperactor/src/actor.rs), and the [RDMA runtime](https://github.com/meta-pytorch/monarch/blob/dd1bb6719b2cf2b6bdf8851df02f092a900e6f5e/monarch_rdma/src/rdma_runtime.rs) spawns `Send` futures onto a multithreaded runtime.

Loom needs a supported way to compose those models. One option is a thread-confined transport engine, with resources created and used on its worker thread and a `Send + Sync` command handle exposed to Monarch. Another is a shareable resource API whose synchronization satisfies the negotiated libfabric threading mode. Replacing `Rc` with `Arc` or adding `unsafe impl Send/Sync` alone does not establish correctness.

The worker can belong to Monarch; Loom does not need its own actor framework. The missing contract is which resources and operation leases can cross threads, which calls require serialization, and where destruction runs. Types can encode thread confinement or an established sharing policy, with setup validation for provider-dependent assumptions.

### Accepted operations must survive their observers

Monarch's [posted-operation state](https://github.com/meta-pytorch/monarch/blob/dd1bb6719b2cf2b6bdf8851df02f092a900e6f5e/monarch_rdma/src/backend/ibverbs/queue_pair.rs) retains local memory, registration views, outstanding work identifiers, and the first error until posted work retires. Its [backend submission path](https://github.com/meta-pytorch/monarch/blob/dd1bb6719b2cf2b6bdf8851df02f092a900e6f5e/monarch_rdma/src/backend/ibverbs/manager_actor.rs) can return a timeout while the worker still owns those resources. The [Python readiness tests](https://github.com/meta-pytorch/monarch/blob/dd1bb6719b2cf2b6bdf8851df02f092a900e6f5e/python/tests/test_rdma_readiness_and_operations.py) also exercise an eagerly submitted transfer whose returned observer is discarded.

Loom's Rust [async endpoint](bindings/rust/src/async_cq.rs) provides unsafe borrowed-buffer operations and correctly documents that dropping their futures does not cancel accepted work. Those calls are not yet an owned operation facility that can underpin a safe batch API. Their generated integer context identifiers are passed through the [C++ bridge](include/loom/cxx_bridge.hpp) as pointers; an integer token is not valid context storage when the negotiated mode requires `FI_CONTEXT` or `FI_CONTEXT2`. The [upstream context contract](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_getinfo.3.md) requires actual stable, provider-owned scratch storage.

Provide an owned operation state or explicit retention hooks that let the consumer retain the endpoint, registration, allocation, and stable native context until retirement. Keep the application identifier outside the provider's context slots. Submission failure, completion, cancellation, observer drop, and endpoint shutdown must have distinct transitions; a deadline or the first batch error must not free resources for other accepted operations. Buffer-access obligations also survive a timeout: retaining the allocation does not permit the caller to mutate or reuse it while DMA may still touch it.

### Rust needs structured backpressure and shared completion dispatch

The bridge's `unwrap` helpers convert submission errors to `std::runtime_error` containing only a message. Rust receives these as `Error::Cxx`; [is_would_block](bindings/rust/src/error.rs) recognizes only `Error::WouldBlock`. Consequently the presence of that enum variant does not give a backend a reliable `FI_EAGAIN` retry path. Preserve numeric submission status across FFI and distinguish work that was accepted from work that must be retried. Completion errors already preserve a context and numeric code; the submission path needs comparable precision.

The current async operations each consume their CQ until their own context appears and discard unmatched successful events. That is unsuitable for concurrent batches sharing a queue, and for draining work after its observer disappears. Provide a usable shared dispatcher or a low-level polling interface with explicit ownership rules, preserving every completion for its owner. Batch draining, bounded retry, and shutdown must compose with that interface. Monarch can retain its batching and rail policies; Loom must preserve enough information to account for each accepted operation exactly once.

### Progress must outlive local requests

Monarch's [verbs CQ actor](https://github.com/meta-pytorch/monarch/blob/dd1bb6719b2cf2b6bdf8851df02f092a900e6f5e/monarch_rdma/src/backend/ibverbs/cq_actor.rs) tracks expected completions to decide when to poll. Libfabric's [manual-progress requirements](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_domain.3.md) also apply to targets performing only remote memory access, even when no CQ event is generated. Therefore an exported region may require a running progress service for its entire advertised lifetime, not just while the exporting process awaits a local operation.

Rust needs a budgeted progress path that can run independently of individual futures and work with providers that offer no native wait descriptor. The current [AsyncCompletionQueue constructor](bindings/rust/src/async_cq.rs) requires such a descriptor. A manual polling fallback and a correct wait/arming path serve different provider configurations; manual progress does not itself imply that a descriptor is unavailable. A dedicated background thread is optional, but an idle target must continue making the progress promised by its chosen configuration.

### Registration views must preserve device and allocation identity

Monarch's [local-memory cache](https://github.com/meta-pytorch/monarch/blob/dd1bb6719b2cf2b6bdf8851df02f092a900e6f5e/monarch_rdma/src/local_memory.rs) stores `IbvMemoryRegionView` entries, so adopting Loom requires a consumer-side cache/view adaptation. The corresponding Loom requirement is a registration lease and bounded subview usable from Rust: retain the MR and allocation, preserve the owning domain and opaque local descriptor, and derive remote addresses according to the actual MR address model. Verbs' 32-bit rkey is not an appropriate general representation of libfabric's 64-bit key.

The [verbs registration path](https://github.com/meta-pytorch/monarch/blob/dd1bb6719b2cf2b6bdf8851df02f092a900e6f5e/monarch_rdma/src/backend/ibverbs/domain.rs) illustrates why a pointer and length are insufficient for GPU memory. It selects the owning CUDA context, identifies and aligns the allocation, exports a DMA-BUF, and tracks the requested view's offset. Loom has C++ HMEM and DMA-BUF registration paths, but Rust exposes neither. The complete registration request described in priority 3 must cross the bridge, including memory interface, device, DMA-BUF offset, and applicable binding requirements. A subview must not accidentally expose or transfer the entire underlying allocation.

Registration and allocation retention must compose through invalidation, remote release, outstanding DMA, and eventual deregistration. GPU completion must also have an explicit visibility contract before consumers treat the data as usable. Advanced verbs features such as implicit ODP and indirect registrations are separate performance/parity questions; ordinary correct GPU registration is the first requirement, not reproducing every provider-specific optimization.

### Advertised support must be precise enough for backend selection

Monarch's [backend compatibility check](https://github.com/meta-pytorch/monarch/blob/dd1bb6719b2cf2b6bdf8851df02f092a900e6f5e/monarch_rdma/src/backend.rs) currently matches backend variants with available remote contexts. A generic Loom variant would not by itself establish that two independently selected provider stacks can communicate. Loom must expose enough provider/protocol, address-format, MR-mode, and endpoint-address information for the adapter to establish a compatible profile and reject mismatches. Serialize endpoint address bytes and remote registration metadata; local address-vector handles and local MR descriptors are not portable wire identities. The versioned wire envelope and peer-selection policy belong in Monarch.

Memory support also affects admission. Monarch's `register_all` tries every spawned backend and rolls back the registration when any one fails; its [action router](https://github.com/meta-pytorch/monarch/blob/dd1bb6719b2cf2b6bdf8851df02f092a900e6f5e/monarch_rdma/src/action.rs) chooses the first compatible backend rather than retrying other backends after a transfer fails. Enabling a CPU-only Loom backend globally could therefore break GPU-buffer creation that existing backends otherwise support. Loom needs explicit memory-interface support information and useful unsupported-registration errors. Monarch must either enable that backend only for a compatible configuration or change its per-buffer admission policy; a host-only experiment should not advertise general GPU readiness. Device-specific registration failures can still occur after capability checks and must remain ordinary handled errors.

### What belongs in the readiness milestone

For a first CPU integration, prioritize Rust registered RMA and discovery, structured submission errors, stable contexts and operation retention, shared completion dispatch, and target-side progress. These are prerequisites for a credible backend, not optional performance improvements. Then exercise GPU registration and views, allocation reuse, and provider-specific completion/visibility requirements before claiming support for Monarch's GPU workloads.

Monarch still needs backend registration, serializable peer metadata, an actor/worker adapter, and a cache representation that can hold Loom registrations. Those are consumer integration changes rather than missing Loom protocols. Topology, multirail striping, batch aggregation, and higher-level fallback policy should stay with Monarch.

Use the consumer-shaped experiments above together with Monarch's existing [CPU tests](https://github.com/meta-pytorch/monarch/blob/dd1bb6719b2cf2b6bdf8851df02f092a900e6f5e/python/tests/test_rdma_cpu_no_torch.py), [action tests](https://github.com/meta-pytorch/monarch/blob/dd1bb6719b2cf2b6bdf8851df02f092a900e6f5e/python/tests/test_rdma_action.py), [readiness/lifetime tests](https://github.com/meta-pytorch/monarch/blob/dd1bb6719b2cf2b6bdf8851df02f092a900e6f5e/python/tests/test_rdma_readiness_and_operations.py), and [local-memory cache tests](https://github.com/meta-pytorch/monarch/blob/dd1bb6719b2cf2b6bdf8851df02f092a900e6f5e/python/tests/test_rdma_local_memory_cache.py) to define acceptance. None were run against a Loom backend during this review. The goal is to establish that a Rust consumer can preserve its existing correctness guarantees through Loom while keeping established transport choices available for compile-time specialization.

## NCCL network plugin requirements

### Scope and a feasible first target

A host-memory-only implementation can advertise `NCCL_PTR_HOST`, as NCCL's [socket backend](https://github.com/nvidia/nccl/blob/3e46c089f4ae4732722a419eb6096aead7e47a30/src/transport/net_socket.cc) does, and add GPUDirect support later. Loom already has [registered explicit-peer tagged operations](include/loom/core/messaging.hpp), [RMA operations](include/loom/core/rma.hpp), and [nonblocking CQ polling](include/loom/async/completion_queue.hpp). A basic plugin therefore does not require a new collective algorithm layer. The gaps are the contracts and information needed to compose these primitives into correct NCCL callbacks.

NCCL's function-pointer ABI does not require erasing Loom's type-level contracts internally. The adapter can select a compiled transport profile during initialization and route callbacks to that implementation. Fixed ABI limits and chosen request/tag bounds can remain compile-time constants, checked against the supported NCCL and libfabric headers and validated against provider resources during setup.

### Connection setup needs complete addresses and owned connection events

NCCL provides a **128-byte bootstrap handle**. `listen` must return a usable listener without waiting for a peer; `connect` and `accept` report incomplete setup by returning success with a null communication object. An RDM implementation can build those logical connections using address exchange and an application handshake. The handshake, connection identifiers, and compact bootstrap envelope belong in the plugin. A provider address or multirail description need not fit entirely in the bootstrap handle; a separate nonblocking exchange can carry the remaining metadata.

Loom must preserve the actual provider address and its length through endpoint-name lookup, serialization, and AV insertion. The current [address variant](include/loom/core/address.hpp) covers only unspecified, socket, InfiniBand, and Ethernet address classes, while [endpoint-name lookup](include/loom/detail/impl/endpoint_impl.hpp) uses a fixed 256-byte temporary buffer. Together with the address-format conversion gaps in the upstream audit, this prevents treating arbitrary provider addresses as faithfully supported. Offer a complete typed representation for supported profiles or an owned representation that preserves provider bytes and format, with size negotiation and explicit unsupported-format errors.

There is an additional confirmed source defect if the plugin chooses libfabric connected endpoints: [event_queue::poll and wait](include/loom/detail/impl/event_queue_impl.hpp) read a `fi_eq_cm_entry` but discard `entry.info`. Under the [upstream connection-event contract](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_eq.3.md), that `fi_info` is application-owned, identifies the connection request, and is needed to create the endpoint for acceptance or obtain the rejection handle. Dropping it loses the normal accept/reject path and leaks its allocation. Reading only the fixed structure also provides no storage for connection private data. Return an owned connection-request object with the required information and private-data lifetime. Preserve ordinary EQ read failures separately from `FI_EAVAIL`, and check `fi_eq_readerr` itself; the current implementation attempts an error read after every negative result and ignores its return value.

Fixing that CM path is required for a connected-endpoint implementation, while an RDM implementation can proceed through its own handshake. Neither choice removes the need for bounded setup progress, clear errors, and cleanup after incomplete setup.

### Tag negotiation and receive-group ordering are separate contracts

NCCL's `irecv(n, ...)` describes **n independent messages**, each with its own tag, destination buffer, registration, and capacity. It is neither one scatter/gather message nor libfabric's `FI_MULTI_RECV`, which receives multiple messages into a shared buffer. Loom's existing tagged operations can be the primitive underneath the group; the plugin owns aggregation.

The [NCCL matching contract](https://github.com/nvidia/nccl/blob/3e46c089f4ae4732722a419eb6096aead7e47a30/plugins/net/README.md) requires send/receive groups to match in posting order. Tags select a member of the earliest matching group, rather than permitting an unrestricted search through all outstanding groups. Simply translating every NCCL tag to a libfabric tag and posting all groups is not a sufficient argument for correctness. A plugin can enforce the rule with a checked protocol, for example group sequencing and connection isolation where endpoints are shared. Sequence wrap and reuse must not allow an old message to match a new group.

The concrete Loom gap is that [fabric hints and endpoint attributes](include/loom/core/fabric.hpp) do not expose `mem_tag_format`. The [upstream tag-format contract](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_endpoint.3.md) includes reserved upper bits and format-specific field/mask restrictions; this checkout also defines named tag formats. Preserve those semantics rather than treating the field as an arbitrary bitmask or assuming all 64 bits are available. A tag layout and its capacity can be compile-time parameters, validated against the selected endpoint before any connection becomes usable. Message-ordering requirements must likewise be requested or checked, not inferred from reliable delivery alone.

### Group admission must compose with backpressure and fixed request budgets

For `isend` and `irecv`, success with a null request means NCCL will retry. A grouped receive must not post some members, return null, then repost those members on retry. If the plugin accepts a logical group into an internal queue, it owns the work, buffers, and progress obligations; if it returns null after partial native progress, it needs persistent state that resumes exactly that group. Capacity reservation alone does not eliminate provider `FI_EAGAIN` after an earlier member was accepted.

Loom needs exact submission outcomes, stable contexts, and a nonblocking progress path that permit this accounting. The plugin can own the group state machine; a new atomic multi-receive transport primitive is not required. In particular, submission callbacks may need to drive progress before returning null. If no request was returned, NCCL has nothing to pass to `test`, so relying exclusively on that callback can prevent retry from ever succeeding.

The [current ABI constant](https://github.com/nvidia/nccl/blob/3e46c089f4ae4732722a419eb6096aead7e47a30/src/include/plugin/nccl_net.h) is `NCCL_NET_MAX_REQUESTS = 32`. The plugin documentation requires capacity for that many outstanding requests per communication object and proportionally more sends for grouped receives. Pools must also budget the underlying native operations, protocol messages, flush work, and teardown bookkeeping. These are useful compile-time bounds when checked against configured resources. `test` must dispatch completions for all requests sharing a CQ, preserve asynchronous failures, and return promptly when the requested operation is incomplete. Loom already provides `poll_batch`; the missing integration contract is ownership and fair progress across shared work, not the mere existence of batch polling.

### Byte counts, zero-byte messages, and ABI widths need explicit handling

NCCL allows receive capacities larger than the matching sends. `test` must return the actual size of each receive in the original array order and declare the group done only when its promised completion condition holds. Truncation must remain an error. Send completion sizes must come from retained submission metadata, because [libfabric CQ `len`](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_cq.3.md) is not defined as a general send-byte count. A shared completion representation needs field-validity rules so consumers cannot mistake an unavailable value for zero transferred bytes.

The v12 submission sizes are `size_t`, while completion-size arrays and flush sizes are `int`. A plugin must choose and enforce an advertised per-request bound that is representable throughout the callback path; advertising a large provider limit alone does not resolve the callback ABI. Splitting one request into smaller native operations does not make an overflowing aggregate completion size representable. Loom should preserve wide lengths internally and expose the real transport limits. Plugin-selected caps can be compile-time constants established during setup.

Zero-byte messages still participate in matching and completion. The NCCL proxy explicitly accounts for zero-byte sends, and [libfabric tagged operations](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_tagged.3.md) permit zero-byte messages without ordinary IOV/registration requirements. A path through Loom must not turn such a send into a missing protocol event or require registering an empty allocation merely to obtain a request. Its cache currently rejects zero-length registration; that is not a reason to reject zero-length messaging. Cover zero, short, exact-capacity, truncation, and boundary-size cases separately.

### GPU receive completion needs a proven visibility path

`iflush` is a concrete GPU-visibility obligation, not a synonym for polling a CQ. NCCL's [receive proxy](https://github.com/nvidia/nccl/blob/3e46c089f4ae4732722a419eb6096aead7e47a30/src/transport/net.cc) distinguishes network completion, any required flush, and publishing readiness to the GPU. Its [topology logic](https://github.com/nvidia/nccl/blob/3e46c089f4ae4732722a419eb6096aead7e47a30/src/graph/paths.cc) decides when flushing is needed, with `forceFlush` allowing a plugin to require it. The [verbs implementation](https://github.com/nvidia/nccl/blob/3e46c089f4ae4732722a419eb6096aead7e47a30/src/transport/net_ib/p2p.cc) uses a loopback RDMA read and completion, flushing across the participating devices.

Loom needs a documented way to establish the applicable visibility guarantee and express the required operation for each supported provider/device profile. This may be a provider-supported readback or another validated mechanism supplied by the plugin. Ordinary registration support, `FI_FENCE`, and `FI_DELIVERY_COMPLETE` do not by themselves prove that a running GPU observes the bytes. Libfabric's [RMA completion rules](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_rma.3.md) and [memory-domain discussion](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_mr.3.md) require a more specific argument. Nor is `fi_tx_flush` equivalent: it starts queued submissions, not GPU cache/visibility synchronization.

A no-op flush is valid only when the selected configuration already provides the needed guarantee. Otherwise the plugin needs a real operation with observable completion, or must avoid advertising that GPU path. Keep the profile's established visibility policy available for static dispatch, while retaining checks for device- and configuration-dependent facts. CUDA policy need not all live inside Loom, but the transport interface must support the chosen mechanism without losing its registration, peer, ordering, or completion requirements.

### Optional receive completion must not retire native storage too early

NCCL can initialize the `irecv` request slot with the sentinel `NCCL_NET_OPTIONAL_RECV_COMPLETION` for LL/LL128 protocols. It permits an optimization because those protocols inspect flags in the data, but the plugin must still return a valid request that NCCL can test. A first implementation can ignore the optimization and report ordinary completion; it must recognize the slot as an input hint and replace it with an appropriate output.

If the plugin completes that request early, native receive contexts and registrations may still be live. Also, when `irecvConsumed` is implemented, the [proxy](https://github.com/nvidia/nccl/blob/3e46c089f4ae4732722a419eb6096aead7e47a30/src/transport/net.cc) retains the receive request value and passes it back after the GPU consumes the data. Immediate request-slot recycling at `test(done = 1)` can therefore give that later callback the identity of an unrelated operation. Define separate lifetimes for provider completion, NCCL-visible completion, GPU consumption, and reusable storage. Preserve required state until every relevant obligation has ended.

This strengthens priority 6: exactly-once terminal reporting is necessary, but is not always the last use of a request identity. LL/LL128 optimizations also require validating data/flag visibility and ordering for the actual transport, rather than assuming the presence of a completion or fence supplies those properties.

### Device properties and registration scope must describe actual guarantees

NCCL uses `getProperties` to make topology and protocol choices. Loom currently lacks a public projection of libfabric's [NIC device, PCI bus, and link attributes](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/include/rdma/fabric.h). Expose available facts with accurate units and ownership, preserving unknown values. The plugin can derive NCCL's `pciPath`, identity, speed, port, rail, and plane metadata, supplementing discovery where necessary. Loom should not invent a portable mapping for topology information the provider does not supply, or require its own topology planner.

`ptrSupport`, `maxRecvs`, `maxComms`, and size limits must describe the plugin's complete implementation, not just provider capabilities. Supporting HMEM in one registration path does not automatically establish DMA-BUF support, GPU visibility, or every advertised concurrent request count. Virtual NIC fusion and `maxMultiRequestSize` are additional capabilities; neither must be advertised beyond the implemented path. The socket backend uses `maxRecvs = 1` and `maxMultiRequestSize = 1`.

The optional `regIsGlobal` property requires special care. The [documented contract](https://github.com/nvidia/nccl/blob/3e46c089f4ae4732722a419eb6096aead7e47a30/plugins/net/README.md) includes preregistration through one connection, fast registration of contained subranges through other connections, and final release. Loom's [host MR cache](include/loom/core/mr_cache.hpp) already looks up containing ranges, but its HMEM/DMA-BUF lookups create new registrations and unused entries normally remain until eviction. Add or expose a suitable pin/release policy if this cache is to implement the global promise. A per-domain MR may be shareable, whereas an endpoint-bound MR has additional constraints; neither is automatically process-global. A plugin can instead maintain its own cache or leave `regIsGlobal` disabled.

### Communicator configuration and teardown need scoped ownership

The [v12 loader and lifecycle](https://github.com/nvidia/nccl/blob/3e46c089f4ae4732722a419eb6096aead7e47a30/src/plugin/net.cc) call `init` for each communicator and `finalize` for that context. Device enumeration is shared more broadly. A plugin must distinguish process/device resources from communicator-owned connections and operations, so finalizing one communicator cannot invalidate another's registrations, CQs, or progress engine. This is another acceptance case for Loom's resource-lifetime and fallible-close contracts, including failures during partially completed setup.

NCCL also passes a per-communicator `trafficClass`, and v12 has an optional `setNetAttr` callback with algorithm, protocol, and concurrency information. These are consumer configuration and tuning inputs. If the plugin promises QoS support, Loom needs an appropriate endpoint/domain configuration path: libfabric has `tclass` attributes, but the current Loom discovery structures omit them. The mapping is plugin/provider-specific; NCCL's integer is not automatically a libfabric DSCP encoding. Unsupported tuning features are not a reason to block an otherwise correct minimal plugin, but must not be advertised as implemented.

### Keep collective offload and GIN as separate milestones

`ncclCollNet_v12_t` is an optional collective-offload interface, with reduction support queries and windowed/scattered collective transfers. The presence of Loom's [collective wrappers](include/loom/core/collective.hpp) alone does not establish those semantics, supported datatypes, HMEM behavior, or provider support. Assess that path separately if collective offload is desired; NCCL can run its own collectives over an ordinary `ncclNet` plugin.

GPU-initiated networking is also separate. This checkout selects [GIN v14](https://github.com/nvidia/nccl/blob/3e46c089f4ae4732722a419eb6096aead7e47a30/src/include/plugin/gin/gin_v14.h), with device contexts, symmetric registration, progress, signal properties, and error reporting. [GIN v13](https://github.com/nvidia/nccl/blob/3e46c089f4ae4732722a419eb6096aead7e47a30/src/include/plugin/gin/gin_v13.h) additionally exposes host `iput`, `iget`, and `iputSignal` callbacks. A Loom-backed GIN effort would need a supported device/proxy protocol and proven write-before-signal semantics; generic host RMA and atomics are insufficient evidence. These are future consumer requirements, not prerequisites for a host-driven network plugin.

## NVSHMEM and Open MPI consumer requirements

### Scope and how Loom would help

This pass inspected NVSHMEM at `cffd2a512787cdd08dce21453c3296b2908ad432`, Open MPI at `873cd3a294c7194a5f88937de36d5bc0b1c18d88`, and Loom through `534c9753a909da5a61112952c366faf27f2eb15f`. Libfabric contracts and provider behavior were checked against the local checkout identified in the upstream audit. This is a source assessment, with no consumer migration, compiled reproductions, or hardware tests in this pass.

NVSHMEM's [libfabric transport](https://github.com/nvidia/nvshmem/blob/cffd2a512787cdd08dce21453c3296b2908ad432/src/modules/transport/libfabric/libfabric.cpp) combines per-domain registrations, endpoint/CQ/counter setup, RMA, native or staged atomics, retries, and host/proxy synchronization. Loom could consolidate the resource and submission mechanics, make registration/address-model mismatches harder to express, and specialize provider paths after setup validation. NVSHMEM would retain symmetric-heap management, processing-element addressing, GPU proxy policy, signal/acknowledgment protocols, and the definition of its `quiet` and `fence` operations. Its staged atomic protocol is substantive consumer functionality, not boilerplate that a generic wrapper automatically removes.

Open MPI has several distinct consumers. The [OFI MTL](https://github.com/open-mpi/ompi/blob/873cd3a294c7194a5f88937de36d5bc0b1c18d88/ompi/mca/mtl/ofi/mtl_ofi.h) implements tagged MPI matching, synchronous-send acknowledgments, probing, and cancellation. The [OFI BTL](https://github.com/open-mpi/ompi/blob/873cd3a294c7194a5f88937de36d5bc0b1c18d88/opal/mca/btl/ofi/btl_ofi_component.c) supports one-sided RMA/atomics and an optional message path. The [common OFI layer](https://github.com/open-mpi/ompi/blob/873cd3a294c7194a5f88937de36d5bc0b1c18d88/opal/mca/common/ofi/common_ofi.c) handles discovery, locality, resource sharing, and memory monitors. The separate [usNIC BTL](https://github.com/open-mpi/ompi/blob/873cd3a294c7194a5f88937de36d5bc0b1c18d88/opal/mca/btl/usnic/btl_usnic_component.c) uses datagram endpoints and provider-specific behavior. Loom could supply common transport ownership and checked operation building blocks while leaving MPI matching rules, datatype packing, process discovery, and scheduling in Open MPI. These paths must not be treated as one interchangeable set of requirements.

There is especially strong evidence for compile-time specialization here. Open MPI's [specialization documentation](https://github.com/open-mpi/ompi/blob/873cd3a294c7194a5f88937de36d5bc0b1c18d88/ompi/mca/mtl/ofi/README.md) and [current isend generator](https://github.com/open-mpi/ompi/blob/873cd3a294c7194a5f88937de36d5bc0b1c18d88/ompi/mca/mtl/ofi/mtl_ofi_isend_opt.pm) generate functions with constant CQ-data choices and select the appropriate function after discovery. Loom could express that choice through templates and checked profiles instead of requiring a consumer to maintain a generator for transport variants. The gain is a simpler way to preserve the same specialization, not proof of a performance improvement. Runtime backpressure, variable lengths, and asynchronous failures still require handling.

### RDM atomics are present but do not carry the complete operation

Both NVSHMEM and Open MPI's [atomic BTL operations](https://github.com/open-mpi/ompi/blob/873cd3a294c7194a5f88937de36d5bc0b1c18d88/opal/mca/btl/ofi/btl_ofi_atomics.c) pass an explicit destination to libfabric. Loom's [core atomic operations](include/loom/core/atomic.hpp) and [atomic injection](include/loom/detail/impl/atomic_impl.hpp) instead pass `FI_ADDR_UNSPEC`; their signatures provide no peer. A remote address/key identifies memory within a peer, not the destination endpoint itself. These wrappers therefore cannot directly express the consumers' multi-peer RDM atomic operations.

Compare-and-swap has a second concrete loss: Loom accepts registrations for comparison and result buffers but always passes a null descriptor for the replacement operand. The [upstream atomic interface](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_atomic.3.md) provides all three descriptors. Null may be legal for a selected registration mode, but the wrapper cannot support a replacement operand requiring local registration. Carry the peer and every applicable descriptor through base, fetch, compare, vector/message, and typed convenience paths.

NVSHMEM also uses `fi_atomicmsg`, `fi_fetch_atomicmsg`, and `fi_compare_atomicmsg` with `FI_INJECT` for short-lived host input operands and a registered result buffer. Loom's atomic wrappers lack the corresponding per-call message flags. Under upstream's contract, atomic `FI_INJECT` releases **constant input buffers** on return; it does not release the output/result buffer before completion. Preserve that distinction, the selected completion guarantee, and the inject-size/interface restrictions.

Operand lifetime deserves an explicit contract. Open MPI copies an operand into its pending completion object before submission. Loom's typed helpers take operands by `const T&`, accept temporaries, and submit ordinary asynchronous atomics without retaining a copy or requesting injection. That is a lifetime hazard unless the caller retains the referenced values through completion; it is not proof that every use of those helpers fails. Support stable caller-owned operation state, owned operands, or a validated inject path, and document borrowing precisely. No per-operation heap allocation is required by this requirement.

Atomic validity queries are **already present** in Loom (`is_valid`, `is_fetch_valid`, `is_compare_valid`) and expose supported counts. Preserve them when constructing specialized operation/type/count paths. Do not infer universal support from a provider name. Likewise, the [provider-aware atomic wrapper](include/loom/core/provider_atomic.hpp) now delegates its legacy staged entry point to the provider atomic interface; it does not implement NVSHMEM's software protocol. A generic read/modify/write fallback would not preserve atomicity. The upstream atomic contract also limits concurrent use across different atomic actors, so a CPU/GPU/NIC fallback cannot assume those mechanisms are mutually atomic without an established coherence guarantee.

### Quiet requires a completion watermark with established semantics

NVSHMEM explicitly requests `FI_DELIVERY_COMPLETE` in discovery. For non-EFA paths it binds selective-completion CQs and a counter, increments a submitted-operation count after acceptance, then calls `fi_cntr_wait(counter, submitted_ops, timeout)` during `quiet`. Its EFA path instead drains CQ contexts and accounts for staged atomic acknowledgments. Open MPI's [BTL discovery](https://github.com/open-mpi/ompi/blob/873cd3a294c7194a5f88937de36d5bc0b1c18d88/opal/mca/btl/ofi/btl_ofi_component.c) and [TX-context setup](https://github.com/open-mpi/ompi/blob/873cd3a294c7194a5f88937de36d5bc0b1c18d88/opal/mca/btl/ofi/btl_ofi_context.c) also request delivery completion. These consumers establish the meaning of a completion before using it to satisfy a higher-level remote-completion guarantee.

Loom has counters, endpoint-counter binding, and selective CQ binding. The missing pieces are composability and fidelity: [fabric hints](include/loom/core/fabric.hpp) cannot request TX/RX default operation flags, and [counter::wait](include/loom/core/counter.hpp) uses a threshold fixed when the counter is created. There is no public wait-on-this-watermark operation. A caller can build a polling loop from `read()`, but cannot directly express NVSHMEM's changing native wait threshold. [get_error](include/loom/detail/impl/counter_impl.hpp) also collapses the error count into a generic I/O error rather than exposing the count for diagnostics and accounting.

Add a dynamic watermark wait, preserve numeric error counts, and expose the defaults and per-call flags that establish the promised completion level. Keep the counter monotonic while operations are being accounted for; resetting or decrementing it to imitate a new threshold needs a separate synchronization argument. The [counter contract](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_cntr.3.md) counts successful completions independently of whether CQ entries are requested, so a counter-based path must still preserve its CQ error/progress handling. GPU visibility remains a separate requirement where applicable.

This suggests a useful compile-time distinction between a transport configured for buffer reuse and one configured for remote delivery. It does not justify adding a generic `quiet` that silently assumes every counted completion means remote completion.

### Batched RMA needs destinations, flags, and a way to finish a batch

NVSHMEM constructs `fi_msg_rma` with local IOVs, per-buffer descriptors, remote IOVs, explicit target, context, and optional immediate data. It also uses `FI_MORE` on intermediate transfers and preserves the endpoint while the batch is deferred. Loom's [RMA vector wrappers](include/loom/core/rma.hpp) support multiple remote IOVs but hard-code `FI_ADDR_UNSPEC` and pass zero flags. The explicit-peer scalar helpers do not fill that gap: they cannot express the combined vector, immediate-data, and flag requirements.

Provide one complete RMA message representation and make the convenience paths preserve its semantics. Expose and validate both local and remote IOV limits, use reusable descriptor storage where allocation-free progress matters, and retain accepted work across retries. The [upstream batching contract](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_rma.3.md) makes ending a `FI_MORE` sequence significant: the next transmit without `FI_MORE`, or the supported explicit transmit flush, starts deferred work. A frontend must not leave an accepted final operation waiting indefinitely for a later submission. Batch-start flushing, remote-delivery completion, and GPU visibility are three different concepts.

### MPI probes need peek/claim flags and a reservation lifetime

Open MPI uses `FI_PEEK | FI_COMPLETION` for probing, `FI_PEEK | FI_CLAIM | FI_COMPLETION` for matched probing, and a later `FI_CLAIM` receive to consume the reserved message. Loom's [receive flags and translation](include/loom/core/messaging.hpp) expose completion, more, and multi-receive, but no peek, claim, or discard flags. The tagged-message function exists, yet cannot express this use of it through the supported flag vocabulary.

Add those operations with their full [upstream semantics](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_tagged.3.md). A probe is asynchronous. `FI_ENOMSG` in its CQ error entry means no matching message, not a broken fabric. A successful peek-and-claim reserves a message, and the same native context must be used for the later claim receive. That storage must remain valid after the probe completion and must not be reinitialized or returned to a general pool while the reservation remains active. `FI_DISCARD` can provide an explicit way to dispose of a claim where supported; destruction must follow a defined policy rather than silently losing it.

This is a good candidate for a typed claimed-message object whose legal operations are consume or discard. Keep dynamic matching results dynamic, while using types to prevent consuming the reservation twice. Preserve message length, tag, CQ data/source information, and the distinction among no-match, truncation, cancellation, and transport failure. Loom already exposes `fi_cancel`; the additional requirement is a coherent state/lifetime contract, not another cancellation wrapper.

### CQ format and source-preserving reads are compatibility requirements

NVSHMEM opens data-format or provider-selected CQs and calls `fi_cq_readfrom` to attribute incoming staged-atomic messages and replies. Open MPI's MTL uses tagged entries; its one-sided BTL and usNIC path can use context-only entries. Loom's [CQ creation](include/loom/detail/impl/completion_queue_impl.hpp) always requests `FI_CQ_FORMAT_TAGGED`, and its readers use `fi_cq_read`, losing the source-address array. Declaring a `cq_format` enum does not make creation or decoding configurable.

The format restriction has a concrete consequence: upstream [usdf_cq.c](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/prov/usnic/src/usdf_cq.c) selects context, message, or data operations and rejects other formats with `-FI_ENOSYS`. Loom's hard-coded tagged CQ therefore cannot serve that provider's inspected path. Add format-aware creation and matching native-entry decoding; do not simply change the creation flag while continuing to read an array of tagged entries. CQ format is a natural compile-time choice for entry type, stride, and field availability.

Preserve source addresses on normal reads, including batches, and preserve error metadata needed for attribution. Ordinary numeric errors already survive Loom's core CQ path; the missing behavior is full metadata and operation-aware dispatch. Open MPI's probe no-match, receive truncation, and cancellation callbacks demonstrate why an error queue is not just a stream of fatal transport failures. NVSHMEM's remote CQ-data events additionally reinforce the requirement to handle events without a local operation context.

### Scalable endpoints need configurable contexts and checked receive addresses

Open MPI configures scalable endpoint counts, creates individual TX/RX contexts, binds their queues, and uses `fi_rx_addr(peer, context_index, rx_ctx_bits)` to address the correct remote receive context. Its BTL passes `FI_DELIVERY_COMPLETE` in TX-context attributes. Loom [creates contexts](include/loom/detail/impl/scalable_endpoint_impl.hpp) with null attributes; its [public scalable-endpoint interface](include/loom/core/scalable_endpoint.hpp) offers no attribute overrides or endpoint-name method. Its AV exposes `rx_ctx_bits`, but there is no corresponding checked receive-context address helper.

Complete the chain: selected context counts and limits, per-context attributes, endpoint address exchange, CQ/counter binding, and remote receive-context addressing. The [upstream AV contract](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_av.3.md) requires the address encoding to use the same bit count as the AV. Context indices and bit widths can be statically bounded where known, then validated against the actual endpoint. Context handles must also have a documented relationship to their parent endpoint's lifetime.

Threading is a property of the resource group. NVSHMEM serializes host submissions against proxy CQ progress under `FI_THREAD_COMPLETION`; Open MPI selects thread-safe or domain-serialized operation and can partition work across contexts. The [upstream domain contract](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_domain.3.md) requires serialization across objects sharing a completion mechanism, not merely a lock on each endpoint. Loom already exposes threading modes. It needs documented grouping and ownership rules that let consumers satisfy them without redundant locks or unsafe concurrent progress. Traits may remove locks only when that whole contract has been established.

### HMEM registration and provider caches must compose with consumer allocators

NVSHMEM registers a region in each relevant domain, distinguishes local-only from remotely accessible memory, uses CUDA/DMA-BUF metadata, and binds/enables MRs when `FI_MR_ENDPOINT` requires it. Open MPI's [MTL registration](https://github.com/open-mpi/ompi/blob/873cd3a294c7194a5f88937de36d5bc0b1c18d88/ompi/mca/mtl/ofi/mtl_ofi_mr.c) distinguishes CUDA, ROCm, and Level Zero memory and conditionally uses `FI_HMEM_DEVICE_ONLY` for allocations that are not unified memory. That flag is a registration flag, distinct from the memory interface, access permissions, and MR mode. Loom's existing `register_hmem` does not expose it or a general registration-flags argument. This extends the complete registration request in priority 3; device-only and managed/shared allocations must not be collapsed into the same unexamined policy.

There is also a second cache layer beyond Loom's own MR cache. Open MPI's [common OFI code](https://github.com/open-mpi/ompi/blob/873cd3a294c7194a5f88937de36d5bc0b1c18d88/opal/mca/common/ofi/common_ofi.c) can open libfabric's `mr_cache` service, import a memory monitor, and notify it from allocation-release hooks. This integrates the provider cache with the allocator/memory-hook machinery already owned by the application. The [upstream MR documentation](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_mr.3.md) describes this service. Loom currently exposes no such integration.

For consumers needing it, provide an optional, version-checked monitor/service integration with clear callback lifetime, lock, notification, and teardown rules. Calling Loom's own `invalidate` does not notify a separate provider cache. Conversely, not every consumer requires a custom monitor: a functioning provider monitor and explicit registration lifetimes may be sufficient. Allocator interposition is not a mandatory Loom default. The goal is to let an existing consumer supply its established allocation-lifetime information without maintaining two conflicting monitor systems.

### The usNIC path exposes prefix and asynchronous-AV gaps

Open MPI's usNIC transport requests `FI_MSG_PREFIX`, reads `msg_prefix_size`, and reserves provider header space when laying out buffers. Loom can represent the mode bit but does not expose the prefix size in its endpoint attributes or provide a prefix-aware buffer contract. Per the [upstream mode contract](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_getinfo.3.md), this memory is provider-owned prefix space, not application payload. Expose its size and the corresponding length/offset rules, or reject that mode before presenting an ordinary payload-only interface. A compile-time layout can use a validated prefix bound; an arbitrary fixed header size is not a provider guarantee.

The [usNIC module](https://github.com/open-mpi/ompi/blob/873cd3a294c7194a5f88937de36d5bc0b1c18d88/opal/mca/btl/usnic/btl_usnic_module.c) also uses asynchronous AV insertion. Loom explicitly rejects asynchronous AV creation today, which is an honest unsupported feature rather than a silent implementation defect. Supporting this consumer would require AV/EQ binding, insertion progress, and correct generic EQ events in addition to the CM events discussed in the NCCL assessment. Under [libfabric's AV contract](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_av.3.md), insertion can produce per-address errors followed by a final non-error completion even when every address failed. The insertion context must survive that sequence. A single terminal callback on the first error would be incorrect.

This broadens the existing event-queue finding: Loom currently reads successful events as `fi_eq_cm_entry` and does not preserve the context/data of generic `fi_eq_entry` events. Correct decoding needs the event kind and its corresponding layout. Prefix buffers and asynchronous AVs are requirements for this particular Open MPI transport, not prerequisites for every OFI MTL/BTL or NVSHMEM profile.

### Existing support to preserve and useful next experiments

Avoid turning this assessment into a list of APIs that merely need new names. Loom already has atomic validity queries, counter objects, selective CQ binding, endpoint cancellation, scalable endpoint objects, and HMEM registration. Its [endpoint option implementation](src/endpoint_options.cpp) correctly translates its own option constants to upstream names, including the CUDA-API-permission option used by NVSHMEM. Different public numeric values there are not a defect. Extend upstream-backed checks for those translations while retaining the compile-time design.

The highest-value additions are complete RDM atomics and RMA messages, established delivery-completion defaults with dynamic counter waits, peek/claim lifetimes, and CQ format/source fidelity. Scalable contexts, allocator monitors, and usNIC-specific requirements can be prioritized according to the intended consumer profile.

| Experiment                                                                                                                  | What it should establish                                                                                                                                         |
| --------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Two RDM peers issue fetch-add and compare-and-swap with registered inputs/results; delay provider access to input operands. | Explicit destination and all descriptors survive; borrowed/owned/injected inputs obey their distinct lifetimes; atomic validity limits are enforced.             |
| Repeated `quiet` snapshots after mixed writes and atomics, with selective CQ completions and an injected counter error.     | Each accepted operation is counted once at the promised completion level; dynamic thresholds work; failures cannot be mistaken for successful remote completion. |
| Submit vectored RMA with `FI_MORE`, backpressure, and an explicitly ended batch.                                            | Local/remote IOV bounds, destination, data, and flags survive; accepted deferred work is eventually started without duplication.                                 |
| Probe with no match; then peek-and-claim, poll unrelated work, and receive or discard the claim.                            | No-match is ordinary probe output; the claimed message cannot be stolen; its context stays stable beyond the first completion.                                   |
| Use context, data, and tagged CQ profiles, including `readfrom` batches and context-free remote events.                     | Native entry layout, field validity, source attribution, and error dispatch are correct for each profile.                                                        |
| Address several receive contexts from multiple threads under `FI_THREAD_COMPLETION`.                                        | `rx_ctx_bits`, context selection, parent lifetime, and submission/progress serialization agree.                                                                  |
| Release and reuse allocations while both a consumer cache and provider cache are active.                                    | Notifications reach the intended cache layer, avoid reentrant teardown, and prevent stale registration reuse.                                                    |
| For a usNIC-compatible profile, use prefix buffers and partially failing asynchronous AV insertion.                         | Payload offsets are correct; each insertion context survives all error records and its final completion.                                                         |

These are proposed acceptance tests, not results from this pass. They should start with deterministic provider mocks for delayed access and error sequences, then run on appropriate software providers and hardware. Loom would help these consumers most by preserving the exact transport guarantees they already depend on and making established choices static, while leaving MPI and NVSHMEM protocols with their respective libraries.
