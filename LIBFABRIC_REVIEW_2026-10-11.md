# Loom implementation and performance review

Loom still has correctness problems in its Asio and sender interfaces, incomplete paths for several libfabric registration and endpoint models, and potentially substantial overhead in completion dispatch and registration caching. The highest-priority follow-ups are the supposedly blocking Asio operations and premature retirement of multi-receive operations. Both can let callers reuse storage while native work remains outstanding.

This is a broad investigation backlog, not a patch proposal or a claim that every supported provider is broken. This review changed no implementation or test files in either repository. Temporary probes and build output are outside the repositories.

Review date: 2026-10-11. Core inspection began at Loom `8292f83`; the report snapshot is `b99624096cdaf72a274b22dea0ad6614919f19f2`. The intervening commits add Rust HMEM registration and change Monarch RMA submissions; the inspected C++ core is unchanged. Concurrent uncommitted Rust CUDA-option work is outside this snapshot and was left untouched. The libfabric reference is the adjacent checkout at `a79c42e5d`. Runtime checks linked an installed libfabric 2.7.0, rather than a fresh build of that reference checkout.

Priorities are provisional: **P1** means potentially unsafe behavior or a broken fundamental contract in the affected configuration; **P2** means an actionable compatibility, functionality, or performance issue; **P3** means a narrower limitation or design question. **Demonstrated** means a focused runtime or compilation probe; **source-backed** means the implementation and native contract establish the finding; **investigate** means the end-to-end consequence still needs verification. Hardware-specific consequences remain unverified unless explicitly stated.

## Correctness and incomplete implementations

| ID  | Priority | Evidence      | Finding                                                                        |
| --- | -------- | ------------- | ------------------------------------------------------------------------------ |
| C1  | P1       | Source-backed | Asio blocking send and receive return after submission                         |
| C2  | P1       | Demonstrated  | Async multi-receive completes before the provider releases the buffer          |
| C3  | P2       | Demonstrated  | Loom registered buffers do not compile through the Asio submission path        |
| C4  | P2       | Source-backed | Async messaging and atomic senders omit necessary peers or registrations       |
| C5  | P2       | Source-backed | Named RMA query profiles request target capabilities, not initiator guarantees |
| C6  | P2       | Source-backed | Raw MR keys have no complete export and import path                            |
| C7  | P2       | Source-backed | Cache and Rust APIs cannot complete endpoint-bound registration                |
| C8  | P2       | Source-backed | Shared receive contexts have no Loom receive submission interface              |
| C9  | P2       | Source-backed | Receive frontends accept context-only CQs and report zero bytes                |
| C10 | P2       | Investigate   | Inherited FI_MORE can indefinitely defer an awaited operation                  |
| C11 | P3       | Source-backed | Completion metadata is still lost at some wrapper boundaries                   |

**C1 — Implement actual completion semantics for blocking Asio operations.** In [basic_endpoint.hpp](include/loom/asio/basic_endpoint.hpp), `send` at line 516 and `receive` at line 531 call the asynchronous core endpoint methods and immediately return the first buffer's capacity as the transferred byte count. Neither waits for a CQ completion. In particular, a posted receive can report success before any message arrives, and a caller following the documented blocking contract may inspect or free its buffer too early. Both calls also supply no operation context and process only the first buffer in a sequence. The central defect is submission being presented as completion; partial sequence handling is secondary. The [libfabric messaging contract](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_msg.3.md) distinguishes acceptance from completion. Follow up with a delayed peer and a short receive, then either implement blocking completion or expose these as explicitly asynchronous submission methods.

**C2 — Reject multi-receive defaults in one-completion frontends, or implement their full lifetime.** [recv_operation_state::start](include/loom/execution/operation_state.hpp), line 260, and [basic_endpoint::async_receive](include/loom/asio/basic_endpoint.hpp), line 287, inherit `rx_attr.op_flags`, including `FI_MULTI_RECV`. [CQ dispatch](src/completion_queue.cpp), line 123, unregisters on the first event; the sender completes and the Asio context destroys itself. Libfabric permits multiple message completions before the terminal `FI_MULTI_RECV` completion releases the buffer. A mock probe confirmed both frontends complete on a first ordinary receive event and leave the terminal event unclaimed. This proves premature logical retirement; a hardware use-after-free was not exercised. See [multi-receive placement](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_msg.3.md) and [buffer-release flags](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_cq.3.md). Keep contexts and buffers alive through release, or reject the incompatible default for these APIs.

**C3 — Connect registered buffer types to actual Asio submissions.** [registered_buffer.hpp](include/loom/asio/registered_buffer.hpp) supplies free `buffer_sequence_begin/end` functions in `loom::asio`, but [asio_context::prepare_buffers](include/loom/asio/asio_context.hpp), line 355, calls the qualified `::asio` functions. The registered buffer classes have neither member `begin/end` nor a conversion accepted by that overload set. Compiling `ep.async_send(const_registered_buffer, handler)` fails with no matching `buffer_sequence_end/begin`, using Asio 1.36.0. This is the intended use illustrated by the registered-buffer header. There is a second integration gap: messaging initiation supplies no descriptor, so fixing iteration alone would still lose the MR. Follow up with compile-and-submit coverage that checks the native descriptor for each registered buffer, including a sequence of independently registered buffers.

**C4 — Complete the async messaging and atomic operation parameters.** Sender messaging in [operation_state.hpp](include/loom/execution/operation_state.hpp), line 209, and Asio messaging in [basic_endpoint.hpp](include/loom/asio/basic_endpoint.hpp), line 249, construct messages without a destination or local descriptors. This leaves sends at `FI_ADDR_UNSPEC`, so callers cannot select an RDM peer, and cannot satisfy local/device registration requirements through those interfaces. Atomic senders in [execution/rma.hpp](include/loom/execution/rma.hpp), lines 234 and 370, likewise hardcode an unspecified peer and null input/comparison registrations. Their result registration does not register their internally copied operands. These gaps are separate from the now-implemented registered, explicit-peer async RMA read/write paths. See [messaging](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_msg.3.md), [atomics](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_atomic.3.md), and [FI_MR_LOCAL and FI_MR_HMEM](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_mr.3.md). Follow up by carrying peer and registration parameters through each frontend and testing both connected and RDM endpoints.

**C5 — Clarify and correct the direction of the RMA discovery profiles.** [fabric_query.hpp](include/loom/fabric_query.hpp), line 53, defines `rdma_write_ops` as `rma | remote_write` and `rdma_read_ops` as `rma | remote_read`. Under [fi_getinfo](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_getinfo.3.md), `FI_REMOTE_WRITE/READ` request permission to be a target; `FI_WRITE/READ` request initiator functionality. Once direction modifiers are specified, `FI_RMA` does not promise every direction. Consequently these profiles do not guarantee that the selected endpoint can initiate the operation suggested by their names. No provider failure was reproduced. Decide whether the profiles describe initiators, targets, or both, and verify returned native capability masks accordingly.

**C6 — Implement or explicitly reject FI_MR_RAW export.** Discovery exposes the raw-MR mode, but [memory_region::key](src/memory.cpp), line 223, and [remote_memory::from_mr](include/loom/core/memory.hpp), line 290, still export a plain `fi_mr_key` value. There is no wrapper path for `fi_mr_raw_attr`, peer `fi_mr_map_raw`, and eventual unmapping. Those steps are mandatory under [FI_MR_RAW](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_mr.3.md). This is relevant to an existing provider: [UCX discovery](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/prov/ucx/src/ucx_init.c) advertises the mode, and [UCX domain control](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/prov/ucx/src/ucx_domain.c) implements raw-key mapping. Exchanging the current descriptor alone is insufficient. Add an owned raw-key exchange/mapping abstraction, or fail ordinary export for this mode rather than presenting it as usable metadata.

**C7 — Make endpoint-bound registration usable through caches and Rust.** [FI_MR_ENDPOINT](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_mr.3.md) creates disabled MRs that require endpoint binding followed by enable. Core C++ exposes both operations. However, [mr_cache](include/loom/core/mr_cache.hpp) only registers, takes no endpoint, and its `mr_handle::mr()` returns a const MR. Rust's [MemoryRegion](bindings/rust/src/lib.rs) also exposes no bind/enable operations, despite discovery representing the endpoint mode. [CXI provider attributes](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/prov/cxi/src/cxip_info.c) provide concrete configurations requiring it. These convenience paths therefore cannot independently produce usable registrations for that contract. Design endpoint-specific cache identity and lifetime, add the missing Rust lifecycle, or reject those modes at the relevant factory. Native handle escape hatches do not complete the typed interface.

**C8 — Add receive submission to shared receive contexts.** [shared_rx_context](include/loom/core/shared_context.hpp), line 101, can be created and bound to a CQ/counter, but has no receive methods. The [messaging helpers](include/loom/core/messaging.hpp) require `endpoint&`, which this type is not. Libfabric requires posting directly to an SRX, as described in [shared contexts](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_endpoint.3.md); binding an ordinary endpoint to it does not supply the missing Loom API. Follow up with a common receive-capable interface and an SRX integration test. Native `fi_recv` calls remain an escape hatch, so this is an incomplete wrapper rather than a claim that the native feature is unusable.

**C9 — Validate receive CQ formats before promising byte counts.** Loom accepts `cq_format::context`. [read_cq_entries](include/loom/detail/impl/completion_queue_impl.hpp), line 58, correctly leaves absent fields zero, while [receive sender completion](include/loom/execution/operation_state.hpp), line 175, and [Asio completion_size](include/loom/asio/asio_context.hpp), line 243, treat that zero as the actual received length. Successful nonempty receives can therefore report zero bytes. [Libfabric CQ formats](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_cq.3.md) make the absence of length explicit. Reject incompatible receive queues or expose an unavailable-length result. This does not affect send/RMA operations that derive their completion size from submitted state.

**C10 — Investigate FI_MORE inheritance across an await.** The same inheritance used to preserve fence/delivery semantics also preserves `FI_MORE` for every async operation. A single operation followed by an await may never post the later non-`FI_MORE` operation needed to flush a provider batch. This is a provider-dependent liveness concern: [fi_msg](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_msg.3.md) permits deferred starts, and [EFA posting code](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/prov/efa/src/efa_data_path_ops.h), line 75, gates native batch completion on the flag being absent. Loom has no typed TX/RX flush helper. Existing async tests even inherit `FI_MORE`, but their mocks complete immediately. Follow up on a batching provider; either constrain allowed async defaults or define a reliable batch-finalization operation. A hardware hang has not been reproduced.

**C11 — Preserve truncation and Rust diagnostic metadata.** [completion_queue::read_error](src/completion_queue.cpp), line 327, preserves several native error fields but omits `fi_cq_err_entry::olen`, the discarded byte count on truncation. Rust's [CompletionEvent](bindings/rust/src/lib.rs), line 299, and [encode_completion](bindings/rust/src/bridge.cpp) additionally omit receive-buffer location, source, provider error code, and diagnostic bytes now retained by core C++. This limits truncation diagnosis and prevents the Rust event from representing full multi-receive/source semantics. See [CQ completion fields](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_cq.3.md). Prioritize fields according to supported frontend features, and distinguish unavailable fields from legitimate zero values.

## Performance findings

| ID    | Priority | Evidence      | Finding                                                                      |
| ----- | -------- | ------------- | ---------------------------------------------------------------------------- |
| PERF1 | P2       | Demonstrated  | Completion registration and FIFO dispatch scale quadratically                |
| PERF2 | P2       | Demonstrated  | HMEM and DMA-BUF cache lookups never reuse registrations                     |
| PERF3 | P2       | Demonstrated  | Small registered messaging and vectored RMA allocate temporary arrays        |
| PERF4 | P2       | Source-backed | Asio FD polling is absent and only the first queue sets the timer interval   |
| PERF5 | P2       | Source-backed | Host-cache misses scan earlier entries under one exclusive lock              |
| PERF6 | P2       | Source-backed | Rust managed operations hold an exclusive endpoint borrow through completion |
| PERF7 | P2       | Source-backed | Rust polling fallback sleeps one millisecond after an empty poll             |

**PERF1 — Replace or bound the linear callback registry.** [completion_registration::bind_to](src/completion_queue.cpp), line 82, scans all outstanding registrations for duplicates; [dispatch](src/completion_queue.cpp), line 131, scans again to find each event. New entries go at the head, so FIFO completions repeatedly find the oldest entry near the tail. Registering and completing N outstanding operations takes O(N²) comparisons, protected by a CQ mutex. A release-build mock benchmark observed:

| Outstanding operations | Registration time | FIFO dispatch time |
| ---------------------- | ----------------- | ------------------ |
| 512                    | 0.108 ms          | 0.109 ms           |
| 2,048                  | 1.675 ms          | 1.713 ms           |
| 8,192                  | 27.364 ms         | 26.161 ms          |
| 32,768                 | 456.475 ms        | 481.563 ms         |

These are one-run wrapper-only timings, not NIC throughput predictions. The approximately quadratic growth is consistent with the source. Consider an indexed context registry with reserved capacity, retaining the current rule that unknown contexts are never dereferenced. Measure realistic queue depths and completion order before choosing the replacement.

**PERF2 — Implement device registration reuse or make these APIs explicitly uncached.** [lookup_hmem](include/loom/core/mr_cache.hpp), line 474, and `lookup_dmabuf`, line 431, unconditionally create and retain a new entry. A mock test performed 100 identical HMEM lookups with each handle immediately released: 100 registrations remained cached, with hits and misses both reported as zero. Another 100 identical DMA-BUF lookups added 100 registrations. Provider-internal caching may reduce native registration cost, but Loom still allocates entries, retains MRs, and misrepresents lookup statistics. Follow up with keys covering allocation/device identity, permissions, DMA-BUF identity and offset, plus invalidation and capacity policy. This is a still-current item from the older reports.

**PERF3 — Remove avoidable hot-path allocations where measured worthwhile.** [descriptors_to_raw](include/loom/core/messaging.hpp), line 133, allocates a vector for descriptors. [readv_to/writev_to](include/loom/core/rma.hpp), lines 143 and 262, allocate descriptor and remote-IOV vectors. A counting-allocation probe measured one allocation for a one-IOV registered `sendmsg` and two for a one-IOV registered `writev_to`, before provider work. Asio constructs additional per-operation IOV storage. Separately, [event_queue::poll](src/event_queue.cpp), line 84, allocates its native read buffer on every poll, including empty polls, and [fabric_service::poll_once](include/loom/asio/fabric_service.hpp), line 278, copies its queue vector. Candidate approaches include inline storage for common small counts, caller-owned prepared descriptors, and reusable read buffers; benchmark separately from provider allocations.

**PERF4 — Implement the advertised Asio wait strategy and respect queue options.** [fabric_service_options](include/loom/asio/fabric_service.hpp), line 54, advertises `use_fd_polling=true`, but nothing reads that option. The service always uses a timer, normally 100 microseconds, and line 294 selects only `completion_queues_.front()->opts.poll_interval`. A later queue requesting a shorter interval is not honored. This can add avoidable completion latency, periodic wakeups, and sensitivity to registration order. Actual latency depends on application-driven polling and scheduler behavior; no latency benchmark was run. Follow up with FD integration that observes libfabric's `fi_trywait` contract and a deliberate policy for differing queue intervals.

**PERF5 — Investigate host-cache lookup cost and retention under varied workloads.** [find_existing_entry](include/loom/core/mr_cache.hpp), line 600, walks backward from `upper_bound` through every earlier entry until it finds a containing region. Nonoverlapping misses can scan the entire cache, making a growing sequence of misses quadratic overall. Lookup and registration hold one exclusive lock; [handle release](include/loom/core/mr_cache.hpp), line 619, also takes it. There is no automatic registration-count or byte budget. Explicit eviction is available, so unbounded growth is a policy concern rather than proof of a leak. Measure increasing disjoint ranges and multithreaded reuse; consider interval indexing and a documented bounded policy if those workloads matter.

**PERF6 — Allow managed Rust operations to remain outstanding concurrently.** [AsyncEndpoint](bindings/rust/src/async_cq.rs), starting at `send` on line 522, uses `&mut self` for operations that retain that borrow while awaiting completion. Ordinary callers cannot keep a send and receive, or multiple writes, pending together on one endpoint through this interface. This is stronger serialization than thread confinement alone requires and limits pipelining. The raw Endpoint API can submit multiple operations; this finding concerns the managed convenience layer. Investigate submission returning an independent completion ticket, or split handles whose provider access remains correctly serialized.

**PERF7 — Make Rust manual polling latency configurable.** [AsyncCompletionQueue::wait_result](bindings/rust/src/async_cq.rs), line 139, sleeps for one millisecond after an empty poll when no wait FD is available. A completion arriving just afterward waits for the timer unless another progress source or notification wakes the task. This is an explicit documented fallback, not a hidden correctness defect, but may dominate fabric latency for small sequential operations. Evaluate configurable/adaptive polling or an external progress driver; measure CPU cost as well as tail latency. FD-backed waits are a separate path and are not subject to this fixed sleep.

## Earlier findings and validation

The older [correctness report](CORRECTNESS_DEFECTS.md) and [consumer readiness report](CONSUMER_READINESS.md) contain useful history, but should not be treated as a current failure list. Current source includes intended fixes for unique MR keys, offset-based remote addresses, owning connection requests, control-event decoding, collective AV-set inputs and returned group addresses, C++ multi-receive buffer pointers, reserved DMA-BUF registration offsets, ordering conversions, core atomic destinations/descriptors, and registered explicit-peer async RMA. C2 is a frontend retirement defect, distinct from the old missing-buffer-pointer defect. C6 and C7 concern registration modes beyond the ordinary fixed key/address paths. These status observations are not exhaustive provider certification.

Eight selected existing test executables passed: execution progress, Asio vectors, completion dispatch, MR cache, RMA, atomic peers, queue waits, and fabric integration. Together they reported **116 test cases and 6,282 assertions**. This was not the entire test suite; Rust and GPU/NIC-specific integration suites were not run. The temporary build used GCC 16.2.1, installed libfabric 2.7.0, stdexec, and Asio 1.36.0. It needed explicit TBB linkage in this environment; that adjustment was confined to the temporary build configuration.

Focused results:

```text

asio multi_recv: posted=1 first_dispatched=1 completed_before_release=1 terminal_dispatched=0
hmem cache: identical_lookups=100 registrations=100 retained=100 hits=0 misses=0
dmabuf cache: identical_lookups=100 additional_registrations=100 retained_total=200
single_iov allocations: sendmsg=1 writev=2 accepted=1
```

The registered-buffer compile probe separately failed at `asio_context.hpp:355` and `:356`, with no matching Asio sequence functions. Temporary evidence is in `/tmp/loom-audit-20261011/`: `probe.cpp`, `probe-results.txt`, `registered-buffer-compile.txt`, individual `test_*.txt` results, and build logs. Suggested initial investigation order: C1 and C2 for buffer/context lifetime; C3 and C4 for usable registered frontend operations; C5 through C10 according to target providers; then PERF1 through PERF4 with representative queue depths and traffic. Keep lower-confidence leads separate from confirmed defects until their reproduction conditions are established.

## Follow-up: native API use and parameter validation

This second pass examines how plausible or erroneous Loom arguments become native libfabric arguments. It adds **10 findings and six narrower investigation leads**. Several are missing validation rather than failures for well-formed inputs: a thin wrapper can leave validation to callers, but the inconsistent behavior between neighboring Loom interfaces should be deliberate and documented. Provider acceptance in a mock establishes parameter forwarding, not successful or safe network execution.

The follow-up began at `df64c127edf12f72f51de168ad1e942c7972f2b1` and finished inspection at `85c4a8c`. The intervening commit changes Monarch examples, not these core paths. The C++ implementation used by the temporary build is unchanged from the initial report's snapshot. Rust's CUDA-policy additions and concurrently edited Monarch files were left untouched. The libfabric reference and installed runtime are as described above.

| API1  | P1       | Demonstrated with native UDP             | Unsupported operations can dereference absent native operation tables       |
| API2  | P2       | Demonstrated forwarding; native contract | RMA reads receive write-only flags, including through default inheritance   |
| API3  | P2       | Demonstrated                             | Remote-length checks differ by overload and are absent from atomics         |
| API4  | P2       | Demonstrated                             | Remote-region slicing can underflow lengths and wrap addresses              |
| API5  | P2       | Demonstrated                             | Registered C++ operations accept buffers outside the supplied MR            |
| API6  | P2       | Demonstrated                             | Senders can register completion on the wrong CQ and remain pending          |
| API7  | P2       | Demonstrated native-layout fixture       | InfiniBand socket addresses are decoded from the wrong offset               |

**API1 — Apply unsupported-operation checks consistently before native dispatch.** [Free messaging helpers](include/loom/core/messaging.hpp), including `loom::tagged_sendv` at line 940 and `tagged_recvv` at line 982, validate the endpoint handle but directly invoke native operations without checking the relevant operation table or member. A real UDP/DGRAM endpoint returned by installed libfabric 2.7.0 had `ep->tagged == nullptr`. The guarded [endpoint::tagged_send](src/endpoint.cpp), line 224, returned an error; calling the free `loom::tagged_sendv` on the same endpoint in an isolated child terminated with **SIGSEGV (11)**. No transfer or NIC was needed. The [native inline call](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/include/rdma/fi_tagged.h) directly dereferences that table. This requires an unsupported operation to be selected; it is not a claim that valid UDP messaging crashes. Other free messaging, legacy RMA, and triggered helpers deserve the same audit. Follow up with a capability/operation-table matrix, including TX-only and RX-only contexts, and return a consistent unsupported-operation error before dispatch.

**API2 — Make RMA-read flags operation-specific.** [read_to](include/loom/core/rma.hpp), line 389, accepts the general `op_flags` set and forwards injection, transmit-completion, and delivery-completion flags to `fi_readmsg`. The [RMA manual](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_rma.3.md), lines 283–307, defines those flags for `fi_writemsg`. A parameter-capture probe observed all three on an accepted read submission. More significantly, the [read sender](include/loom/execution/operation_state.hpp), line 419, inherits all TX defaults: setting a delivery-completion default for writes also sends `FI_DELIVERY_COMPLETE` on subsequent async reads. A second probe confirmed that path. Rust [rma_flags/endpoint_read_raw](bindings/rust/src/bridge.cpp), lines 334 and 364, similarly allow `RmaCompletion::Transmit` and `Delivery` for reads. Providers may reject or ignore such flags; a resulting transfer failure has not been reproduced. Validate explicit flags and filter inherited flags according to the operation, while preserving meaningful completion and fence semantics. Test reads and writes sharing an endpoint with write-oriented defaults.

**API3 — Enforce the same remote extent across RMA overloads and atomic element counts.** The flagged [read_to/write_to](include/loom/core/rma.hpp), lines 397 and 502, reject a local buffer larger than `remote.length`; the nonflagged overloads at lines 424 and 529 ignore that field. A probe using a 16-byte local buffer and an 8-byte remote descriptor produced one native submission through the basic overload, then a local rejection when merely adding `op_flag::none`. [Atomic submission](include/loom/core/atomic.hpp), line 264, likewise builds a remote element count without relating it to the byte extent: two `uint64_t` elements were submitted against an 8-byte descriptor. The provider only receives address, key, and transfer count, so it cannot enforce a smaller Loom subregion inside a larger valid native MR. Crossing the actual native MR may fail instead; no remote overwrite was performed in the probe. Apply overflow-safe byte/count checks consistently, and test subregions inside larger registrations as well as actual MR boundaries. Also investigate unequal local/remote aggregate lengths in the vector helpers.

**API4 — Check remote-region arithmetic before constructing a descriptor.** [remote_memory_base::offset_by/subregion](include/loom/core/crtp/remote_memory_base.hpp), lines 70 and 82, perform unchecked unsigned addition and subtraction. On this 64-bit system, `remote_memory{0x1000, 7, 8}.offset_by(9)` produced length `18446744073709551615`; `subregion(7, 16)` produced an out-of-bounds 16-byte region; an address near `UINT64_MAX` wrapped to zero. The inflated length can then pass checks in otherwise guarded RMA calls. These inputs are erroneous, but the helpers neither reject them nor document explicit arithmetic preconditions. Rust's [RemoteMemory::subregion](bindings/rust/src/lib.rs), line 74, already rejects corresponding cases. Give C++ an equally clear checked path and define zero-length/end-of-region behavior. Include address-plus-length overflow, not just offset-versus-length checks.

**API5 — Validate that local buffers belong to the supplied registration.** [Asio async_write_to/async_read_from](include/loom/asio/basic_endpoint.hpp), lines 386 and 456, attach one `local_mr.descriptor()` to every submitted IOV, but check only the aggregate remote length. The native buffer need not lie inside `local_mr.address()/length()`. A probe registered an 8-byte array, then submitted a separate 16-byte array; Asio forwarded the unrelated MR descriptor and the full 16-byte IOV. The C++ [MR-taking RMA overloads](include/loom/core/rma.hpp), lines 457 and 562, similarly reduce the region to a descriptor without checking the local range. This is caller misuse under a low-level borrowed-buffer contract, but it is an actionable validation opportunity where Loom already has the required range information. Depending on provider and registration mode, it may cause protection errors or invalid memory access; neither was reproduced on a NIC. Compare Rust's existing [registered_range](bindings/rust/src/bridge.cpp), line 354. Validate each IOV and domain/endpoint compatibility as appropriate, accounting for the nonzero DMA-BUF address distinction noted earlier.

**API6 — Check the supplied sender CQ against the endpoint's actual binding.** [fabric_operation_state_base::register_completion](include/loom/execution/operation_state.hpp), line 105, registers on the caller's `queue_`; it does not verify that native completions for the operation's direction will arrive there. With an endpoint bound to CQ A and its send sender constructed with CQ B, a probe confirmed successful submission, an unhandled completion on A, and no receiver invocation. This is a wrong-parameter hang, not a failure when the caller supplies the correct CQ. Loom already tracks successful native CQ bindings and provides [completion_registration::bind(endpoint, direction, ...)](src/endpoint_bind.cpp), line 20; Asio uses that path. Validate or derive the sender CQ from the binding, covering distinct TX/RX queues and scalable contexts. The probe explicitly retired its mock registration afterward.

**API7 — Decode FI_SOCKADDR_IB as sockaddr_ib, or reject the unsupported representation.** [Address conversion](include/loom/detail/conversions.hpp) maps `FI_SOCKADDR_IB` to `address_format::ib`, but [address_from_raw](src/address.cpp), line 68, copies the first 16 bytes of the whole address as its GID. Native `sockaddr_ib` has family, partition key, and flow information before `sib_addr`; the GID begins at offset 8 in the tested rdma-core layout. A fixture with GID bytes beginning at `0xa0` decoded with first byte `27` (the address family) and a mismatched GID. The [native format contract](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_getinfo.3.md) and [verbs address construction](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/prov/verbs/src/verbs_info.c), line 1118, agree on that structure. Other IB socket fields also have no faithful Loom representation. Separately, provider-specific formats such as EFA/CXI fall through to an unspecified address while callers such as `get_local_address()` still return a successful `result<address>`; this is a representation limitation rather than a demonstrated malformed provider address. Add faithful native/opaque address storage or explicit unsupported-format errors. Rust's raw byte address path is separate.

**API8 — Preserve the stricter deprecated endpoint threading requirement.** [from_fi_threading](include/loom/detail/conversions.hpp), line 429, maps both `FI_THREAD_ENDPOINT` and `FI_THREAD_FID` to `threading_mode::fid`; converting back yields `FI_THREAD_FID`. The [domain contract](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_domain.3.md), line 267, explicitly makes endpoint threading stricter: the same endpoint must be serialized even across transmit and receive flows. A round-trip probe confirmed native value 5 becoming 2. C++ domain attributes and contract checks can consequently report a weaker obligation than the supplied native discovery entry. This is a legacy-mode compatibility issue; no currently selected provider returning that mode or resulting race was demonstrated. Preserve the distinction or conservatively reject it. Rust rejects that lossy input hint, so do not attribute the same hint behavior to Rust.

**API9 — Complete FI_MR_COLLECTIVE registration.** Loom exposes `mr_mode_flags::collective`, and collective calls accept `memory_region*`, but [to_fi_mr_access](include/loom/detail/conversions.hpp), line 29, has no `FI_COLLECTIVE` permission mapping. [Registration](src/memory.cpp) never adds it from the domain mode. A mock domain requiring `FI_MR_COLLECTIVE` accepted a Loom send/receive registration whose native access mask lacked `FI_COLLECTIVE`. The [MR contract](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_mr.3.md), lines 358 and 746, requires this permission, paired with send and/or receive access, when that mode is set. No hardware provider enforcing the mode was exercised; the finding is an incomplete typed registration path. Add an explicit collective permission or reject the unsupported mode before offering a usable collective MR. Test the mask independently of whether a permissive provider happens to accept the descriptor.

**API10 — Complete registration for MR-associated remote-event counters.** `mr_mode_flags::rma_event` is exposed, but [memory_registration and memory_region](include/loom/core/memory.hpp) cannot request `FI_RMA_EVENT` on registration or bind an MR to a counter. The [registration implementation](src/memory.cpp), lines 57 and 127, uses zero flags for ordinary MRs or only HMEM/DMA-BUF flags for attributed registrations. `memory_region::bind` accepts only an endpoint. The [native MR contract](https://github.com/ofiwg/libfabric/blob/a79c42e5de63eadae8e3dfc7e172af639a6161b9/man/fi_mr.3.md), line 309, requires the event flag, counter binding, and then enablement for MRs using those counters under `FI_MR_RMA_EVENT`. Ordinary MRs in the same domain do not necessarily need this sequence; this finding specifically concerns MR-associated counters. Decide whether this feature is supported, then expose the complete sequence or reject it clearly. Endpoint-wide counter binding is not a substitute for MR binding.
